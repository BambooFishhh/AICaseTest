# 后端技术评审 v8.6.2 — LLM 出参契约化

> 版本 v8.6.2，一旦确定尽量不要轻易改动。基线 v8.6.1。任务 9.5–9.8。纯后端版本。

## 一、变更点

### 1.1 校验引擎（9.5）

**pom**：`com.networknt:json-schema-validator:1.5.9`（组件总表授权项；draft-07；1.x 最终版）。

**新增 `service/LlmSchemaValidator.java`**：

```java
@Component
public class LlmSchemaValidator {
    @Value("${llm.schema.mode:observe}") private String mode = "observe";   // 三件套
    private final Map<String, JsonSchema> cache = new ConcurrentHashMap<>();

    public boolean isEnforce();
    public List<String> validateJson(String json, String schemaName);       // 含路径错误列表；非法 JSON 也归入错误
    public List<String> validate(JsonNode node, String schemaName);
    public boolean validateStructured(String json, String schemaName, String caller); // true=通过或 observe 放行
}
```

- classpath `/llm-schemas/{name}.json` 加载 + ConcurrentHashMap 编译缓存；未知 schema 抛 IllegalArgumentException。
- SchemaValidatorsConfig typeLoose=false（严格类型，漂移检测目标即类型错）。

### 1.2 契约定义（9.6）

`backend/src/main/resources/llm-schemas/` 四份 draft-07，`$comment` 记契约来源：

| schema | 形状 | required | 关键约束 |
|---|---|---|---|
| test-cases.schema.json | array | items: title/steps/priority/type | type 枚举 positive·negative·boundary·data；priority P0–P3（对齐 v8.4 白名单）；steps 为字符串数组 |
| prd-analysis.schema.json | object | modules/requirements | 五数组按 PrdAnalysisResult 类型化；requirements.items 必填 title；modules.items 必填 name |
| state-machine.schema.json | array | items: name/states/transitions | transitions.items 必填 from/to（validateTransitions 前置的结构保证） |
| review-result.schema.json | array | items: index/status | index≥0 整数；status 枚举 pass·fix·reject；confidence 0–1 |

顶层一律宽松（未列属性不限制），只钉结构与类型——契约目标是拦"格式漂移"，不是限内容。

### 1.3 统一出口 + 灰度（9.7）

**LlmService**：

- 新增 `chatJson(systemPrompt, userPrompt, temperature, schemaName)` 重载；原三参方法委托 `schemaName=null` 行为不变。
- 校验失败：WARN（schema/caller/mode/错误明细）；observe 放行；enforce → 追加"缺失或类型错误字段清单"重试 1 次 → 仍失败抛 BusinessException(50002)。
- `extractJsonObject` 重写：首个能括号配平的 `{...}` 段（字符串感知 + 转义处理），替代首尾截取；无配平段回落旧逻辑。PrdAgent 内的重复 extractor 保持现状（其输入经 analyze 入口统一走本版校验，extractor 统一不在本期范围）。

### 1.4 Agent 接入（9.8）

注入模式统一（直 new 单测 null 安全）：

```java
private LlmSchemaValidator llmSchemaValidator;
@Autowired(required = false) void setLlmSchemaValidator(...) {...}
```

| 接入点 | 插入位置 | enforce 失败行为 |
|---|---|---|
| TestGeneratorAgent.parseTestCases | extractJsonArray 之后、逐条容错之前 | 抛 BusinessException(50002) → 既有整段上抛重试接管 |
| PrdAgent.analyzeByLlm | extractJsonObject 之后、readValue 之前 | 抛 BusinessException → analyze 既有 50015 包装链路 |
| StateMachineAgent.extract | extractJsonArray 之后、readTree 之前 | 抛 RuntimeException → 与现有解析失败同语义 |
| TestCaseReviewAgent 评审解析 | extractJsonArray 之后、readTree 之前 | 抛 BusinessException(50002) |

偏差说明：数组类出参点 enforce 不做"附清单二次提示词重试"（那是 chatJson 对象路径专属），复用各调用方既有轮次重试——语义等价且不增加新重试层。

### 1.5 测试策略说明

validator 单测覆盖矩阵 + 四 schema 双向样本；chatJson enforce/observe 矩阵基于既有 LlmServiceTest 的 mock 链路模式；parseTestCases 接入经 ReflectionTestUtils.invokeMethod 直测私有方法（最高风险接入点）。其余三个接入点由编译期接线 + validator 单测覆盖（与计划书"每接入点 ≥3 测试"的偏差记录在案：三点均为同一行式调用 `if (v != null && !validateStructured(...)) throw`，风险收敛于 validator 本身）。
