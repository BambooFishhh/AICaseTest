## 3. SpringAnalyzer

### 3.1 字段注入（关键约束：字段初始化默认值）

现有单测（SpringAnalyzerTest 等 5 个）直接 `new SpringAnalyzer()`，不走 Spring 容器——`@Value` 不生效时 int 字段为 **0**，会把全部源码截没。因此必须带字段初始化：

```java
// v7.13: LLM 增强输入预算配置化（原 v6.1 硬编码 16000/1500/30000）。
// 字段初始化默认值兜底：单测直接 new 不走容器，纯 @Value 下 int 为 0 会截没全部源码
@Value("${app.analyzer.spring-source-total-chars:120000}")
private int springSourceTotalChars = 120000;

@Value("${app.analyzer.spring-source-per-file-chars:10000}")
private int springSourcePerFileChars = 10000;

@Value("${app.analyzer.rule-summary-max-chars:80000}")
private int ruleSummaryMaxChars = 80000;
```

`collectSourceSnippets` 中 `int maxTotal = 16000; int maxPerFile = 1500;` 改读字段，其余逻辑（sourcePriority 排序、test 目录排除）不变。

### 3.2 buildRuleSummary 合法化收敛

旧实现（非法 JSON 的根源）：

```java
String json = objectMapper.writeValueAsString(summary);
return json.length() > 30000 ? json.substring(0, 30000) : json;  // 砍出非法 JSON
```

新实现——先减条目再序列化，5 轮收敛（每轮条目 ×0.7），末轮兜底 counts 骨架：

```java
/**
 * v7.13: 超长时先减条目再序列化——旧实现 json.substring(0, 30000) 会把 JSON
 * 砍成非法 JSON 塞进 prompt（下游靠 LLM 容错，本质是把问题推迟）。
 * 每轮条目数 ×0.7 重新序列化，≤ 上限即返回；5 轮后仍超返回 counts-only 骨架。
 * endpointCount 等总量计数始终真实，LLM 可感知"明细被裁剪"。
 */
private String buildRuleSummary(List<EndpointInfo> endpoints, List<EnumInfo> enums,
                                List<EntityInfo> entities, List<BusinessRule> businessRules) {
    double scale = 1.0;
    for (int pass = 0; pass < 6; pass++) {
        Map<String, Object> summary = buildScaledSummary(endpoints, enums, entities, businessRules, scale);
        String json = serialize(summary);
        if (json.length() <= ruleSummaryMaxChars) {
            return json;
        }
        scale *= 0.7;
    }
    // 兜底：counts-only 骨架（合法 JSON，无明细）
    Map<String, Object> skeleton = new LinkedHashMap<>();
    skeleton.put("endpointCount", endpoints.size());
    skeleton.put("enums", enums.size());
    skeleton.put("entities", entities.size());
    skeleton.put("businessRules", businessRules.size());
    skeleton.put("note", "规则明细因超出长度上限省略，仅提供总量");
    return serialize(skeleton);
}

private Map<String, Object> buildScaledSummary(..., double scale) {
    // 条目基线上限仍保留（200/120/200/300）防无界；scale 在基线内再按比例缩减
    int epLimit = (int) Math.ceil(200 * scale);
    int enLimit = (int) Math.ceil(120 * scale);
    int entLimit = (int) Math.ceil(200 * scale);
    int brLimit = (int) Math.ceil(300 * scale);
    // 与旧结构一致：endpointCount 恒为真实总数；businessLogic 单条仍 truncate 200
    ...
}
```

序列化失败（异常）沿用旧兜底 `summary.toString()`。

### 4.2 文件优先级排序（升级 A9）

现状核实：`collectVueFiles` 已有 v7.4(A9) 的绝对路径字典序排序（确定性已有）。但纯字典序下 `src/components/` 排在 `src/views/` 之前——截断时组件把页面挤出预算，优先级反了。

v7.13 将排序比较器升级为"页面优先 + 字典序"：

```java
// collectVueFiles 尾部排序（替换原 Comparator.comparing(File::getAbsolutePath)）：
result.sort(Comparator
        .comparingInt(this::vueFilePriority)
        .thenComparing(f -> f.getPath().replace('\\', '/')));
```

```java
/** v7.13: 页面/路由入口优先（views/pages/App.vue），组件次之，其余最后——截断时保测试价值最高的文件 */
private int vueFilePriority(File f) {
    String p = f.getPath().replace('\\', '/').toLowerCase();
    if (p.contains("/views/") || p.contains("/pages/") || p.endsWith("/app.vue")) return 0;
    if (p.contains("/components/")) return 1;
    return 2;
}
```

确定性语义不变（A9 的"两次分析子集一致"保持），仅截断取舍从"字典序先到先得"变为"页面优先"。
