# 后端技术评审 v7.5 — 缓存与可复现基线

| 项 | 内容 |
|---|---|
| 关联 PRD | `docs/v7.5/PRD_v7.5_缓存与可复现基线.md` |
| 涉及风险条目 | A11 / A15 |
| 数据库 | 新表 `llm_result_cache`（H2 ddl-auto 自动建；MySQL 加 V11 迁移脚本） |

## 1. 架构决策

### 1.1 为什么是自建 DB 缓存而不是 Spring Cache / Redis

| 方案 | 评估 | 结论 |
|---|---|---|
| Spring Cache（现有 CacheManager） | 10 分钟 TTL、进程内（本地模式重启丢失）；"内容未变一直有效"语义不符 | 否 |
| Redis String 直存 | 依赖 Redis（本地开发零依赖原则被破坏）；已有 H2/MySQL 落库先例（code_analysis） | 否 |
| **DB 表 + prompt-hash 键** | 持久化、跨重启、H2/MySQL 双端工作、与实体化分析结果（code_analysis）同构 | **采用** |

### 1.2 缓存键设计（核心）

```text
cache_key = SHA-256( hex( model + "\u0001" + systemPrompt + "\u0001" + userPrompt ) )
```

- **模型名**：`@Value("${llm.model:gpt-4o}")`（与 LlmService 同源配置，不侵入 LlmService）——换模型全量自动失效。
- **systemPrompt + userPrompt 全量入键**：prompt 模板演进（skill 文件修改）自然失效，不需要版本号常量。
- **A15**：userPrompt = `buildRequirementPrompt(prdDocs, contextDocs, supplementary)` 输出——输入文档任何变化（含截断逻辑变化）都改变键。
- **A11**：userPrompt = `enhanceComponentSummary` 的完整 prompt（组件名 + 路由 + 完整源码）——组件源码任何变化都改变键。
- 用 `\u0001` 分隔符防止 "a"+"bc" 与 "ab"+"c" 拼接歧义。

### 1.3 缓存粒度：LLM 原始响应文本

- 缓存 `result_text` = LLM 返回的原始字符串（非反序列化对象）。
- 命中后走**既有解析路径**（`mergeComponentSummary` / PrdAgent 的 JSON 解析）——解析逻辑单一路径，缓存不引入第二套解析分支。
- **毒缓存防护**：A11 写缓存前确认 merge 解析成功；A15 写缓存前确认结果非空（空结果本身抛异常，不进缓存路径）。LLM 返回的合法但语义差的响应仍会被缓存——接受（同输入同输出正是目标，一致性优于单次质量抖动）。

## 2. 代码变更清单

### 2.1 新增 `entity/LlmResultCache.java`

```java
@Entity
@Table(name = "llm_result_cache")
public class LlmResultCache {
    @Id
    @Column(length = 64)
    private String cacheKey;          // SHA-256 hex
    @Column(length = 32)
    private String cacheKind;         // prd_analysis / component_summary
    @Column(columnDefinition = "MEDIUMTEXT")
    private String resultText;        // LLM 原始响应
    private LocalDateTime createdAt;
}
```

新增 `repository/LlmResultCacheRepository.java`（JpaRepository，`existsById`/`findById`/`save`）。

### 2.2 新增 `service/LlmResultCacheService.java`

```java
@Service
public class LlmResultCacheService {
    @Value("${llm.model:gpt-4o}")
    private String model;

    public String get(String kind, String systemPrompt, String userPrompt);
    public void put(String kind, String systemPrompt, String userPrompt, String response);
    // 内部：sha256 key；get 读 result_text（kind 仅供排查，不参与键计算也校验一致）
    // put：existsById → save；DataIntegrityViolation（并发竞争）catch 忽略
    // 全部 try-catch：任何 DB 异常 → log.warn + 返回 null / 静默跳过（降级直调 LLM）
}
```

### 2.3 修改 `agent/PrdAgent.java`（A15）

`analyze(prdDocs, contextDocs, supplementary)` 内：

```java
String requirementText = buildRequirementPrompt(...);
// v7.5(A15): 先查缓存
String cached = llmResultCacheService.get("prd_analysis", systemPrompt, requirementText);
if (cached != null) {
    PrdAnalysisResult result = parsePrdResponse(cached);   // 复用 analyzeByLlm 的解析段
    if (result != null && !result.isEmpty()) { log.info("PRD analysis cache hit"); return result; }
    // 缓存内容解析失败/为空（毒缓存）→ 落回 LLM 路径并覆盖写
}
PrdAnalysisResult result = analyzeByLlm(requirementText);
// 成功后写缓存
llmResultCacheService.put("prd_analysis", systemPrompt, requirementText, lastRawResponse);
```

- `analyzeByLlm` 拆为"调 LLM 拿原始响应"与"解析原始响应"两段（原逻辑不动，只拆方法边界），缓存命中复用解析段。
- systemPrompt 来源与现状一致（chatWithAnalysis 内部构造的话，把构造提出来传给缓存层与 LLM 层共用，确保键与实际调用一致——见实现时确认，若 systemPrompt 在 LlmService 内部拼接，则缓存键退化为只含 userPrompt + model，prompt 变化靠 cache 表 kind 区分度 + 手动清库兜底；**实现时以"键必须覆盖实际发送的 system prompt"为准**）。

### 2.4 修改 `analyzer/VueAnalyzer.java`（A11）

`enhanceComponentSummary(dir, m)` 内：

```java
String prompt = """...""".formatted(...);
// v7.5(A11): 先查缓存
String cached = llmResultCacheService.get("component_summary", SUMMARY_SYSTEM_PROMPT, prompt);
if (cached != null) {
    if (mergeComponentSummary(cached, m)) return;   // merge 返回 boolean 化
    // 毒缓存 → 落回 LLM 路径
}
String response = llmService.chat(SUMMARY_SYSTEM_PROMPT, prompt, 0.2);
if (mergeComponentSummary(response, m)) {
    llmResultCacheService.put("component_summary", SUMMARY_SYSTEM_PROMPT, prompt, response);
}
```

- `mergeComponentSummary` 改返回 boolean（解析成功 true），现有调用点唯一（enhanceComponentSummary），无兼容负担。
- systemPrompt 现为内联字符串常量，提为常量 `SUMMARY_SYSTEM_PROMPT` 供键与调用共用。
- VueAnalyzer 需 `@Autowired LlmResultCacheService`（新依赖，单例注入无并发问题）。

### 2.5 新增 `db/migration/mysql/V11__add_llm_result_cache.sql`

```sql
CREATE TABLE llm_result_cache (
    cache_key VARCHAR(64) NOT NULL,
    cache_kind VARCHAR(32) NOT NULL,
    result_text MEDIUMTEXT,
    created_at DATETIME(6) NOT NULL,
    PRIMARY KEY (cache_key),
    KEY idx_llm_result_cache_kind (cache_kind, created_at)

```

## 3. 关键风险与对策

| 风险 | 对策 |
|---|---|
| systemPrompt 在 LlmService 内部拼接导致键覆盖不全 | 实现时先确认调用链；键必须覆盖实际发送内容，必要时把 systemPrompt 构造上移到 Agent 层 |
| 毒缓存（LLM 返回合法 JSON 但语义差） | 接受（同输入同输出是目标）；解析失败/空结果不写缓存；命中后解析失败自动落回 LLM 路径 |
| 缓存表无限增长 | 无害垃圾；非目标不做清理，V11 索引已含 created_at 便于后续清理 |
| 并发 put 竞争 | 主键约束 + DataIntegrityViolation catch 忽略（两写者内容相同，谁赢都一样） |
| H2 与 MySQL 方言差异 | MEDIUMTEXT 列注解在 H2 端由 ddl-auto 生成为 CLOB，验证启动无异常 |

## 4. 验证计划

1. `mvn test` 全量绿（150 + 新增约 10 个用例）。
2. 手动冒烟：本地 H2 启动，同项目两次分析第二次日志出现缓存命中且 LLM 调用次数下降；改 PRD 一个字后重新调 LLM。
3. MySQL profile（V11 迁移）由用户环境验证，H2 为主验证环境。
