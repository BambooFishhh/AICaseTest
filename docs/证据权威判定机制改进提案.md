## 一、现状审查

现行机制为 v7.10 的 **C2 证据链对账**，由两部分构成：

| 环节 | 位置 | 做什么 |
|---|---|---|
| 新鲜度检测 | `OrchestratorAgent.applyEvidenceStaleness` (L358) | `project.updatedAt` 晚于代码侧最新产物（`CodeAnalysis.createdAt` / `StateMachine.createdAt`）→ `evidenceStale=true` |
| 一致性检测 | `OrchestratorAgent.applyStateFlowConsistency` (L390) | PRD `stateFlows[].states` 与代码 `StateMachine.states` 归一化小写匹配，整条流程零命中 → 冲突 |
| 结果承载 | `PrdAnalysisResult.evidenceStale` (L33) / `evidenceInconsistencies` (L35) | `boolean` + `List<String>` |
| 生成侧注入 | `TestGeneratorAgent` (L3084-3094) | 拼 `context.evidenceConsistency` 进 prompt |

### 缺陷 1：口径自相矛盾

同一轮生成的 prompt 里存在两种互斥权威指令：

- 冲突标注文案（`applyStateFlowConsistency` L428-429）：`"…，以代码为准，需人工确认"`
- 生成侧系统提示（`TestGeneratorAgent` L3128）：`"请以 PRD 文档为纲生成测试用例；…代码信息用于补充接口路径与前置状态。"`

前者说代码为真值，后者说 PRD 为纲。LLM 在冲突场景下收到的是矛盾指令，实际取舍不可控——这恰恰是 C2 想要消除的"静默分叉"，只是从链间分歧转移到了 prompt 内部。

### 缺陷 2："需人工确认"没有落点，机制实际是断的

全仓检索 `evidenceInconsistencies` / `evidenceStale` / `evidenceConsistency`，**前端零消费**（`frontend/src`、`projects/*/src` 均无引用）。

含义：所谓人工确认，只是塞进 prompt 的一句话。人看不到任何冲突清单，也无法裁决。对 LLM 而言它是措辞，对人而言它不存在——该机制目前只起到"告诉模型有这个分歧"的作用，闭环从未建立。

### 缺陷 3：粒度过粗，且无方向概念

`applyStateFlowConsistency` 判定逻辑：

```java
for (String state : flowStates) {
    if (codeStates.contains(state.toLowerCase())) { anyHit = true; break; }
}
if (!anyHit) { /* 整条流程记为冲突 */ }
```

两个问题：

1. **链级而非元素级**：一条流程只要命中 1 个状态，整条放过。缺 3 个状态漏 2 个的场景完全不报，漏报率随流程复杂度上升。
2. **无方向**：只判断"有无交集"，不区分「PRD 有代码无」与「代码有 PRD 无」。而这两种方向的业务含义截然相反——前者是未实现或需求废弃，后者是实现溢出或文档滞后。方向信息是判定权威的前提，当前被丢弃。

### 缺陷 4：维度单一

对账只覆盖状态流 1 个维度。而 PRD 解析结果中已有 `modules` / `requirements` / `businessRules` / `entities` 四类结构化数据，代码侧也已有端点、前端表单规则、页面流等产物，均未纳入对账。

## 二、设计原则

### 原则 1：权威归属是函数，不是常量

把"谁是权威"从全局常量改为随上下文变化的判定：

```
authority = f(需求状态, 冲突方向, 证据新鲜度, 冲突维度)
```

### 原则 2：两类用例，两种真值基准

代码回答"系统现在实际怎么跑"（事实），PRD 回答"系统应该怎么跑"（意图）。因此：

- **验证意图的用例**（新功能验收）→ PRD 是基准
- **验证现状的用例**（存量回归）→ 代码是基准

测试用例天然分属这两类，权威跟着用例目的走，而非全局二选一。

### 原则 3：新需求场景下代码不足采信

新需求是在 PRD 之后才实现的。代码可能因理解偏差而跑偏，此时代码是"有缺陷的实现"，不能作为真值基准。判据：需求变更时序晚于代码实现，且需求状态为新增/变更中。

### 原则 4：证据缺失不等于冲突

沿用现有正确做法（无状态机时不判定）。PRD 侧无证据或代码侧无证据，记为"证据不足"并降权，不产生冲突项、不打扰人。

### 原则 5：不阻断生成，但必须可裁决

沿用 C2 的"提示非阻断"语义。冲突不阻塞用例产出，但产出的用例须带待裁决标记，且冲突必须进入人可见的队列——否则等于没做。

### 原则 6：人工裁决要能沉淀

一次裁决不应只解决当下这一条冲突。裁决结果回写为确定性规则，下次同需求、同维度直接套用，避免同一分歧反复打扰——与项目既有的"不指望 LLM 遵从、落库前显式硬兜底"思路一致。

## 三、判定维度细化

### 3.1 维度从 1 个扩到 6 个

| 维度 | PRD 侧证据 | 代码侧证据 | 新增成本 |
|---|---|---|---|
| **状态流转** | `stateFlows[].states/transitions` | `StateMachine.states`(code/name) | 已有，需细化到元素级 |
| **接口契约** | `requirements[].acceptanceCriteria` 中的操作描述 | `CodeAnalysis` 端点(method+path) | 数据已具备，需建对账器 |
| **业务规则** | `businessRules[].rule` | 后端校验 + 前端表单 rules（VueAnalyzer 已提取） | 数据已具备，需建对账器 |
| **数据实体/字段** | `entities[]` | entity/DTO 字段、表结构 | 数据部分具备 |
| **页面/路由** | `modules[]` | 前端路由 / `PageFlow`（`ScopeItem.TYPE_PAGE` 已有） | 数据已具备 |
| **权限/角色** | 需求中的角色与权限描述 | 鉴权注解、路由守卫 | 数据可能不足，列为低优先级 |

建议首批落地 **状态流转 + 接口契约 + 页面/路由** 三个维度：数据最完整、对用例影响最直接。业务规则与实体字段次之。权限维度数据不足，暂缓。

### 3.2 判定粒度提升到元素级 + 方向级

对每个维度输出三类差异，而非一个布尔：

| 输出 | 含义 | 权威倾向 |
|---|---|---|
| `PRD_ONLY` | PRD 有、代码无 | 看需求状态：新增→PRD；稳定→漏实现或已废弃，需人工 |
| `CODE_ONLY` | 代码有、PRD 无 | 看需求状态：新增→疑跑偏，PRD；稳定→文档滞后，代码 |
| `MATCHED` | 两侧一致 | 无冲突 |

**关键改动**：把 `anyHit` 的链级布尔判定，改为逐元素产出差异集合。冲突描述从"流程 X 无对应状态"细化为"流程 X 的状态 `已支付` 在代码状态机中无对应项（该流程其余 4 个状态均有对应）"——后者可直接定位到实现缺口。

## 四、需求状态识别（复用现有数据，不新增人工标注）

项目已有现成语义资产，无需新建需求状态字段：

| 需求状态 | 判定依据（已有数据） | 权威倾向 |
|---|---|---|
| **新增 ADDED** | `ScopeItem.changeKind == ADDED` | PRD |
| **变更中 MODIFIED** | `ScopeItem.changeKind == MODIFIED` | 暂缓（等 PRD 定稿） |
| **受波及/存量 AFFECTED** | `changeKind == AFFECTED`，或不在任何 scope 内 | 视冲突方向，见第五节 |
| **已确认范围** | `ScopeDefinition.status == confirmed` | 提高裁决优先级 |
| **成熟度** | `requirements[].acceptanceCriteria` 非空 | 有验收标准 → PRD 侧证据更强 |

补充时序信号（与新鲜度检测合流）：

- PRD 侧时间 > 代码侧时间，且需求为 ADDED/MODIFIED → **代码侧不可采信，权威归 PRD**
- 两侧时间戳缺失 → 记为证据不足，不判权威

`ScopeItem.origin`（AUTO_DIFF / LLM_MAPPED / MANUAL）可作为置信度权重：`MANUAL` 项的人工意图最明确，冲突时优先提请裁决。

## 五、判定矩阵

权威归属查表（行 = 需求状态，列 = 冲突方向）：

| 需求状态 | PRD 有 · 代码无 | 代码有 · PRD 无 | 两侧均有差异 |
|---|---|---|---|
| **新增 ADDED** | 以 PRD 为准<br>尚未实现，按 PRD 生成 | **不生成**<br>无需求依据（疑实现跑偏） | 以 PRD 为准<br>新增一律以 PRD 为准 |
| **变更中 MODIFIED** | 暂缓 | 暂缓 | 暂缓 |
| **稳定 / 存量 AFFECTED** | 需人工裁决<br>漏实现，或需求已废弃 | **不生成**<br>文档滞后，无需求依据 | 需人工裁决 |

动作只有四类：**以 PRD 为准生成 / 不生成 / 暂缓 / 需人工裁决**。

### 关键原则：用例只来源于 PRD（v13.19 修正）

生成侧 prompt 的原文即"以 PRD 文档为纲生成测试用例；**代码信息用于补充接口路径与前置状态**"，
且项目级本就有"无 PRD 不可生成"的约束（`ProjectDetail.canGenerate` 在 `!hasPrd` 时禁用生成入口、
提示"请先添加 PRD 文档"）。据此：

- **代码不是用例来源**——"代码有、PRD 无"只说明文档滞后，应被记录为文档缺口，**不该产出用例**。
  v13.17 曾把该格判为"以代码为准、按现状回归"，这与"以 PRD 为纲"自相矛盾，已于 v13.19 纠正为
  `skip`（不生成）。注：该格原实现因 `authority=code` 被 prompt 白名单过滤，**实际并未真的生成用例**，
  属**语义标签错误**——但前端「证据冲突」页会误显示"当前权威：以代码为准"，误导判断。
- **变更中不打扰人**——PRD 未定稿时裁决没有意义，人也只能回答"等 PRD 改好"。
  改为暂缓（`deferred`），等 PRD 更新后重跑。实际场景里 PRD 变更中的项目生成入口本就不可用，
  该分支属**防御性兜底**。
- **唯一需要人的格子**——存量稳定下"PRD 说要做而代码没做"：是漏实现还是需求该废弃，机器判不了。

修正后**人工入口从 6 格收敛到 2 格**，其余全由机器决定或干脆不产出。

### 多维度冲突的合成规则

同一需求在多个维度同时冲突时：

1. **合并为一条裁决请求**，不按维度重复打扰。
2. 权威取**最高优先级**：`需人工裁决 > 以 PRD 为准 > 不生成 / 暂缓`。
3. 唯一例外：若冲突维度分属不同需求，各自独立判定，不合并。

优先级方向取"宁问不猜"，但配合原则 6 的规则沉淀，长期打扰量应递减。

### 人工裁决仍保留"以代码为准"

矩阵不再自动产出 `code`，但**人工裁决选项里保留"以代码为准"**——那是人的例外判断
（例如产品确认"PRD 写错了，按实现来"），与机器自动判定性质不同。

## 六、人工确认的触发条件

命中任一即进入人工裁决队列：

| 编号 | 触发条件 | 设计意图 |
|---|---|---|
| T1 | 判定矩阵落入"需人工裁决"格 | 矩阵直出 |
| T2 | `evidenceStale == true` 且冲突涉及 ADDED/MODIFIED 需求 | 代码侧过期，不可采信 |
| T3 | 同一需求 ≥2 个维度同时冲突 | 多点冲突，置信度高 |
| T4 | 冲突落在 `ScopeDefinition.status == confirmed` 的本期范围内 | 已拍板范围，影响面明确 |
| T5 | 冲突涉及 `entities` 中的核心实体 | 影响面大 |
| T6 | 冲突项的 `ScopeItem.origin == MANUAL` | 人工意图明确，机器不应擅自裁决 |
| T7 | 兜底：某维度既无 MATCHED 也无明确方向（证据不足但链路完整） | 防止静默漏判 |

**反向约束（不打扰的条件）**：证据缺失（任一侧无证据）、冲突维度全为 MATCHED、置信度低于阈值且不涉及本期范围。

## 七、处理流程

```
对账（6 维度，元素级 + 方向）
  → 识别需求状态（changeKind / origin / 时间戳 / 成熟度）
  → 查判定矩阵
      ├─ 以 PRD 为准 → 注入生成约束（PRD 优先），不打扰人
      ├─ 不生成 / 暂缓 → 不进生成依据，不打扰人（仅落库留档）
      └─ 需人工裁决 → ① 生成不阻断
                      ② 相关用例标记 verdict=pending + conflictRef
                      ③ 冲突进待裁决清单
                      ④ SSE 提示
                      ⑤ 前端清单可见
                      ⑥ 人工二选一（以代码 / 以 PRD，或标注"需求已废弃"）
                      ⑦ 裁决回写为长期规则 → 下次同需求同维度自动套用
```

### 裁决回写规则的匹配键

规则生效范围建议按 **项目 + 需求锚点 + 维度** 三级匹配：

- 需求锚点用现有 content hash 需求 id（项目已有做法），PRD 局部修改不影响其他规则的命中
- 同键规则存在时直接套用，不再提请裁决
- 规则支持失效：需求被重新解析且锚点变化时，旧规则自然不再命中

### 用例侧标记

待裁决期间产出的用例应携带溯源信息，供人工复核与后续筛选：

- `verdict`：`pending` / `prd_authoritative` / `code_authoritative` / `deprecated`
- `conflictRef`：指向冲突项 id
- `dimension`：冲突维度

人工裁决后，相关用例可批量筛选出来重生成或修正。

### 8.4 建议实施顺序

1. **补齐人工裁决闭环**（前端清单 + verdict 标记）——当前机制完全断链，收益最高
2. **修正 prompt 口径矛盾**——改动小，直接消除模型侧歧义
3. **粒度细化到元素级 + 方向**（状态流转维度）——代价可控，先验证效果
4. **扩展接口契约 / 页面路由维度**
5. **裁决规则回写与命中**
6. 业务规则、实体字段、权限维度（视数据完备度再定）

## 九、风险与权衡

| 风险 | 说明 | 缓解 |
|---|---|---|
| 打扰量上升 | 元素级 + 多维度会显著增加冲突项数量 | 先落地规则回写，让重复冲突自动消化；触发条件从严 |
| 字符串匹配误判 | 元素级匹配更依赖归一化质量，误报可能增加 | 保留"证据不足"分类；对低置信度项降权不报 |
| `project.updatedAt` 误报 | 项目任意编辑都会更新该字段（既有已知问题） | 维持"建议"语义不阻断；后续可改为 PRD 侧专用时间戳 |
| 维度对账器开发量 | 6 维度全建成本高 | 按 8.4 分批，首批仅 3 个 |
| 裁决规则与新 PRD 冲突 | PRD 重解析后旧规则可能过时 | 用 content hash 锚点，锚点变化则规则自然失效 |

| 1 | 实施顺序 | **后端判定核心先行**，前端待裁决清单次之 | 前端清单的展示与交互完全依赖 `EvidenceConflict` 结构，后端先行可避免结构变更导致的返工；且后端可单测闭环验证 |
| 2 | 裁决规则存储 | ~~先落 `SystemSetting`~~ → **实施时改为直接复用已裁决的冲突记录**（见 十一 节说明） | 复用现有 KV 虽无 schema 变更，但会造成"裁决已落库、规则却漏写"的双写不一致；记录表复用则天然原子一致 |
| 3 | 首批维度 | 本轮仅 `STATE_FLOW`；`ENDPOINT` / `PAGE` 下一轮 | 避免同时引入"新匹配器 + 新判定逻辑"两类风险，先把判定矩阵在单维度上跑通验证 |
| 4 | pending 用例 | 照常入库 + 标记，不隔离 | 不阻断生成是既定原则；隔离会造成用例可见性断裂与重复产出。`TestCase.verdict` 列**已于 v13.18 补上**，关联规则取项目级快照 |
| 5 | 版本 PRD | 暂不开新版本号，本提案即设计依据 | 验证通过后再并入正式 PRD / CHANGELOG |

### 读代码后做出的三处设计调整

1. **触发阈值保持"整条流程零命中"不变。** 元素级差异改由冲突项的 `prdSide` / `codeSide` 承载，而不放开阈值。
   原因：匹配基于字符串包含，部分命中场景误报率高（PRD"待支付" vs 代码 `PENDING_PAYMENT`），放开阈值会让噪音淹没真实冲突。原用例 `partiallyHitFlowIsNotConflict` 因此继续成立。

2. **新增 CODE_ONLY 方向（代码有、PRD 无）。** 原实现只判"有无交集"，完全没有方向概念。
   该方向在 v13.19 后一律判为 `skip`——**不生成用例、也不进生成依据**。理由：用例只来源于 PRD，
   而代码状态机含大量内部状态（INIT、DELETED 等），既无需求依据不该产出用例，全量上报也会刷屏。
   冲突本身仍**全量落库留存**，作为"文档缺口"提示（建议补 PRD）；新增需求下 reason 会标注
   "疑实现跑偏，建议复核"，供人按需查看。

3. **需求状态用项目级聚合，不做跨粒度猜测。** `ScopeItem.changeKind` 的粒度是接口 / 状态机 / 页面，与 PRD 状态流并非同一粒度；强行元素级映射会引入脆弱的名称联想，故先做项目级聚合（宁可保守多问，胜过错误自动判定）。

4. **不生成 / 暂缓类冲突不进入「待裁决」视图（v13.19）。** `skip`（无 PRD 依据）与 `deferred`
   （变更中暂缓）虽同样处于未裁决状态，但不该占用人的注意力。清单接口支持 `manualRequired=true`
   过滤，前端「待裁决」视图默认启用；「全部」视图仍可见，作为文档缺口提示。
   （v13.17 原表述为"`authority=code` 不进清单"，语义已随矩阵修正而更新。）

**口径（项目级快照）**：本轮对账只要存在 `authority=human` 的冲突，就把这批最终落库的用例整体标为 `pending`，`conflictRef` 记该批 human 冲突的 key 集合（去重保序），`dimension` 记维度集合。无此类冲突时不写任何字段，保持 null。

### 已完成：覆盖缺口与 PRD 依据对齐（v13.20）

**起因**：回答"如何保证代码与 PRD 不一致时以 PRD 为准"时，逐层核查发现一处**机制内的指令矛盾**：

- `buildCoverageChecklist` 的 `transitions` 取自代码状态机**全部**转换（仅按本期范围过滤，**未与 PRD 状态流做交集**）；
- 这些转换经 `capIdsInto` 进入 `gaps.transitionIds`；
- `hasRemainingGaps` 把 `transitionIds` / `endpointIds` 当作**可验证覆盖项**参与多轮收敛（仅 `componentIds` / `dependencyIds` 被降级为参考上下文）；
- 补齐轮 roundNote 明确要求 **"以下 coverageGaps 仍未覆盖，请优先为这些缺口生成用例"**。

即：证据对账层刚对 CODE_ONLY 判 `skip`（无 PRD 依据不生成），覆盖缺口层同时要求"优先生成"——**同一 prompt 内两条互斥指令**。这是"以 PRD 为准"最薄弱的一环。

**改动**

| 文件 | 改动 |
|---|---|
| `agent/TestGeneratorAgent.java` | `buildCoverageChecklist`：新增 PRD 状态池与转换过滤；新增 `collectPrdStates` / `normalizeStateName` |
| `agent/TestGeneratorAgent.java` | roundNote 补一句"若某个缺口对应 PRD 未描述的功能（仅代码实现中存在），跳过它，不要为其生成用例" |
| `test/.../TestGeneratorAgentChecklistPrdScopeTest.java` | **新增** 10 例 |

**判定口径**（两条边界必须守住）

1. **只排除"两端状态均未被 PRD 状态流描述"的转换**——一端被 PRD 提到即保守保留。理由：字符串匹配无法处理同义不同名（PRD"待支付" vs 代码 `PENDING_PAYMENT`），严格判"两端都在 PRD"会误伤真实流转。
2. **PRD 无状态流时不过滤**——与对账侧"证据缺失 ≠ 冲突"同一原则。若 `stateFlows` 为 null / 空 / 有条目但 `states` 全空，则状态池为空 → **保持原行为**；否则 PRD 未解析出 states 的项目会丢掉全部状态流转覆盖。

状态名归一化（`trim` + 小写）**与 `OrchestratorAgent.readFlowStates` 同口径**，两处判定必须一致。

**范围边界（有意为之）**：本次只收口 `transitions`。`endpoints` 仍取自代码分析——PRD 没有"接口清单"概念可对齐，强行过滤会误伤，故保持现状、改由 prompt 声明约束。`transitionIds` 也**未**整体降级为参考项——那会放松**所有**状态流转的覆盖收敛，只应剔除无 PRD 依据的个别转换。
