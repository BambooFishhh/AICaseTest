# 后端技术评审 v8.6.1 — 向量数据一致性闭环

> 版本 v8.6.1，一旦确定尽量不要轻易改动。基线 v8.5。任务 9.1–9.4。纯后端版本，前端无变更。

## 一、变更点

### 1.1 删除补偿表（9.1）

**Flyway `V14__add_pending_vector_ops.sql`**：

```sql
CREATE TABLE pending_vector_ops (
  id VARCHAR(32) NOT NULL PRIMARY KEY,
  op_type VARCHAR(16) NOT NULL,          -- 目前仅 DELETE
  collection VARCHAR(64) NOT NULL,
  expr TEXT NOT NULL,                    -- Milvus 布尔表达式原样保存
  attempts INT NOT NULL DEFAULT 0,
  last_error TEXT,
  status VARCHAR(16) NOT NULL DEFAULT 'PENDING',   -- PENDING/DONE/DEAD
  next_attempt_at DATETIME(6),
  created_at DATETIME(6),
  updated_at DATETIME(6)
);
CREATE INDEX idx_pending_vector_ops_status ON pending_vector_ops(status, next_attempt_at);
```

**`entity/PendingVectorOp.java` + `repository/PendingVectorOpRepository.java`**：JPA 实体（H2 由 ddl-auto=update 自动建表，对齐既有测试做法）；派生查询 `findByStatusAndNextAttemptAtLessThanEqualOrderByCreatedAtAsc` 与 upsert 用 `findByCollectionAndExprAndStatus`。

**`MilvusService.deleteWithRetry` 终败分支**：注入 `PendingVectorOpRepository`（@Autowired(required=false) setter + 字段默认 null，直 new 单测不受影响）→ 新增包级私有 `recordDeleteFailure(collection, expr, error)`：同 collection+expr+PENDING 已存在则仅刷新 lastError/updatedAt，否则插入新行——重复失败不堆行。

### 1.2 ShedLock 引入 + 补偿重放（9.2）

**pom.xml 新依赖**（组件总表授权项）：`net.javacrumbs.shedlock:shedlock-spring:5.16.2` + `shedlock-provider-jdbc-template:5.16.2`。

**Flyway `V15__add_shedlock.sql`**：官方建表语句（IF NOT EXISTS 双保险）。

**`config/ShedLockConfig.java`**：
- `@EnableSchedulerLock(defaultLockAtMostFor = "PT5M")`
- `LockProvider` bean = JdbcTemplateLockProvider（usingDbTime）
- ApplicationRunner 幂等 `CREATE TABLE IF NOT EXISTS shedlock(...)`——H2 开发/测试环境不走 Flyway，启动兜底建表

**`service/VectorOpCompensationTask.java`**：

```java
@Scheduled(fixedDelayString = "${app.vector.compensation-interval-ms:300000}",
           initialDelayString = "${app.vector.compensation-initial-delay-ms:60000}")
@SchedulerLock(name = "vectorOpCompensation", lockAtMostFor = "PT4M", lockAtLeastFor = "PT30S")
public void replayPendingOps()
```

- 扫描 PENDING 且 next_attempt_at ≤ now（单批 ≤50）；逐条调 `MilvusService.deleteByRawExpr(collection, expr)`（新增公开方法，复用 deleteWithRetry 链路）
- 成功 → DONE；失败 → attempts+1，nextAttemptAt = now + 60s×2^attempts；attempts ≥ `compensation-max-attempts`(5) → DEAD + ERROR
- 整体 try/catch 包裹，调度永不中断

### 1.3 周期对账（9.3)

**Flyway `V16__add_reconciliation_reports.sql`**：id/project_id/db_count/vec_count/drift_ratio/repaired_added/repaired_removed/status(OK|REPAIRED|WARN|SKIPPED)/message/created_at + 项目索引。

**`MilvusService.queryIdsByProject(collection, projectId)`**：QueryParam expr 查询返回该项目全部向量 id；失败返回 **null（区别于合法空集）**——防止 Milvus 宕机被误判"全量缺失"触发重建风暴。

**`service/VectorReconciliationService.reconcileAll()`**：

```java
@Scheduled(cron = "${app.vector.reconcile-cron:0 0 2 * * *}")
@SchedulerLock(name = "vectorReconciliation", lockAtMostFor = "PT30M")
```

- 逐项目：dbIds = testCaseRepository.findByProjectId；vecIds = queryIdsByProject（null → SKIPPED 报告跳过）
- DB 多 → 缺失实体批量 semanticService.indexCases 重建（repaired_added）
- 向量多 → 孤儿 id 走 deleteByIds（终败自动落补偿表，闭环衔接 9.1）（repaired_removed）
- driftRatio = |db-vec| / max(db,1)；> threshold 记 WARN 日志 + 状态 WARN；有修复动作记 REPAIRED，否则 OK
- 每项目一条 ReconciliationReport 落表；汇总 INFO

**`controller/AdminVectorController.java`**：GET `/api/admin/vector/reconciliation` 返回最近 20 条报告（命中 SecurityConfig 既有 `/api/admin/**` ADMIN 角色门禁，无需改安全链路）。

### 1.4 检索侧存在性兜底过滤（9.4）

**`SemanticService`**（testCaseRepository 已注入，零新增依赖）：

- `isDuplicate`：top-1 相似度达标后再验 `existsById(hit.id)`，不存在（幽灵）→ WARN + 幽灵计数器 +1 并放行不判重
- `searchCases`：逐条 findById N+1 改为单次 `findAllById(ids)` 批量往返，按相似度序输出存在项，幽灵项跳过并计数
- 新增 `AtomicLong ghostRecallCount` + getter（为 v8.7 的 milvus_ghost_recalled_total 指标预留）
