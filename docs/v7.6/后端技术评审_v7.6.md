## 1. A17 状态机转换 ground truth 校验

### 1.1 SpringAnalyzer 证据扫描（规则层）

新增 `extractStateTransitions(File dir, List<File> javaFiles)`，对每个 Service/Controller 类（复用 isServiceClass 判断 + Controller 判定）用 JavaParser 扫描：

```java
// 识别赋值点（MethodCallExpr）
// setStatus(X) / setStatus(EnumClass.X) / setStatus(this.status.next()) —— 参数含枚举字面量才有证据价值
// 识别来源条件（同方法体内的条件判断）
// if (getStatus() == PAID) / if (status == PAID) / if (PAID.equals(getStatus()))
```

**from 提取规则**：方法体内条件中出现的枚举值 Y（与 to 同一状态字段）→ from=Y；无条件 → from=`*`。
**to 提取规则**：setStatus 参数解析为简单名（`OrderStatus.PAID` → `PAID`）。
**证据结构**：

```json
{"field": "status", "from": "PAID", "to": "CANCELLED", "method": "cancelOrder", "file": "OrderService.java"}
```

- 归一化：from/to 统一 trim + 大小写不敏感比较（StateMachineAgent 侧匹配时再剥枚举前缀）
- 同方法多证据全收（去重 by field+from+to+method）
- 仅扫非 test 目录（findJavaFiles 已过滤，v7.4 A1）
- **上限 200 条**，超出记 warning

挂载点：`analyze()` 主流程，在 extractDependencyGraph 之后（同为规则层，无 LLM 调用）。结果进 `BackendResult.stateTransitions`（`List<Map<String,Object>>`）。

### 1.2 StateMachineAgent 证据校验

`validateTransitions(List<StateMachine>, boolean withFrontend)` 扩展签名，新增 `List<Map<String,Object>> evidence` 参数：

```java
// 匹配逻辑（对每个 LLM transition）：
// normalize(from), normalize(to) —— 剥枚举前缀（最后一个 . 之后部分），lowercase
// 命中条件：存在证据 e 满足
//   (normalize(e.from).equals(from) || "*".equals(e.from)) && normalize(e.to).equals(to)
// 命中 → item.put("verified", true)
// 未命中 → item.put("unverified", true)
// 状态机 confidence 调整：
//   任一 unverified 存在时 confidence = min(confidence, 0.4)（保持 0.5 以下示弱）
```

- evidence 为空（无后端源码/无赋值点）时**不降级**——无证据不等于错误，保持原 confidence，transition 不加标记（诚实：区分"未校验"与"校验失败"）
- rule_based 兜底路径 transitions 本来为空，不受影响

### 1.3 调用链变更

`AnalysisService.analyze()`：`stateMachineAgent.extract(backendResult, frontendResult)` 内部直接读 `backendResult.getStateTransitions()`，无需改签名。

## 2. L6 expected 断言闭环

### 2.1 共享断言工具 ExecutionAssert（新类，service 包）

从 ExecutionService 移出 `assertExpected` 及其正则/停用词常量，扩展为三层：

```java
public final class ExecutionAssert {
    // verdict: passed / failed / skipped
    static String assertExpected(String expected, Map<String, String> pageState);
    static String describe(String expected, Map<String, String> pageState); // 期望/实际摘要，供 error 字段
}
```

**层 1（URL/标题，保持 v7.0 语义）**：ASSERT_URLISH 触发词命中 → 提取英文 token 与 url+title 包含比较。

**层 2（DOM 文本，新增）**：层 1 未触发或层 1 token 为空时，从 expected 提取关键词：
- 中文短语：`[\u4e00-\u9fa5]{2,}` 连续段
- 英文标识符：`[a-zA-Z][a-zA-Z0-9_-]{2,}`（排除停用词）
- 与 `pageState.textSnippet`（body 文本前 500 字符，v7.3 L5 已提供）做包含比较（均 lowercase）
- **全部命中 → passed；任一未命中 → failed**（关键词数 ≥1 才进入比较）

**层 3（skipped）**：无触发词且无关键词，或 pageState 为空。

关键点：层 1 的 "failed" 判定仅当有触发词且提取到 token；层 2 的 failed 判定仅当提取到关键词——**提取不到可比内容永远 skipped，不误报失败**（继承 E4 原则）。

### 2.2 ExecutionService 程序化模式接入

`state_assert` 分支改用 `ExecutionAssert.assertExpected` + `describe`；textSnippet 摘要（前 120 字符）追加进 coordinates 字段（现有 url= 前缀保留）。

### 2.3 ExecutionAgent Agent 模式接入（E5）

`executeStep` 头部增加类型分流（在现有 input 特判之前/同级）：

```java
String type = step.path("type").asText("");
if ("state_assert".equals(type)) {
    Map<String, String> pageState = playwrightSkill.getPageStatus(sessionId);
    String expected = step.path("expected").asText("");
    String verdict = ExecutionAssert.assertExpected(expected, pageState);
    // 组装 ExecutionStep：strategy="assert", result=verdict,
    // error=failed 时 describe(...), coordinates=url + textSnippet 摘要
    return ...; // 直接返回，不进点击流水线
}
if ("api_call".equals(type)) {
    return skipped step("Agent 模式暂不支持 API 调用步骤");
}
```

- state_assert 分支不截图标注（无点击坐标），但保留一张操作后截图作证据（takeScreenshot）
- E5 修复后 Agent 模式对 state_assert 的行为与程序化模式一致

## 3. G20层3 错误→文案对照表

### 3.1 VueAnalyzer 提取 userFeedbackTexts

新增 `extractFeedbackTexts(File frontendDir)`（规则层正则，扫描全部 .vue/.js）：

```java
// 匹配（大小写不敏感）：
// (ElMessage|Message|\$message)\.(error|success|warning|info)\s*\(\s*['"`]([^'"`]+)['"`]
// 输出：{type: "error|success|warning|info", text: "文案", file: "Xxx.vue"}
// 按 (type+text) 去重，上限 100 条，超限记 warning
```

挂载点：analyze() 主流程（与 apiCalls 同级），结果进 `FrontendResult.userFeedbackTexts`（`List<Map<String,Object>>`）。

### 3.2 SpringAnalyzer 提取 errorMessages

在 extractEndpoints 的 ThrowStmt 处理基础上，新增独立扫描 `extractErrorMessages`（覆盖 Controller/Service 全部类，不只 endpoint 方法）：

```java
// throw new BusinessException("订单不存在") → {exception: "BusinessException", message: "订单不存在", file: "XxxService.java"}
// 仅收 String 字面量参数（非变量/拼接），message 长度 2~100
// 按 (exception+message) 去重，上限 100 条
```

结果进 `BackendResult.errorMessages`。

### 3.3 TestGeneratorAgent 注入

`generatePrdRound` context 构建处（L985 businessRules 之后）：

```java
List<Map<String, Object>> feedbackTexts = new ArrayList<>();
// 前端：frontendResult.getUserFeedbackTexts()
// 后端：backendResult.getErrorMessages() → 转换为 {type:"backend_error", text: message, source: exception}
// 合并去重，上限 60 条
context.put("userFeedbackTexts", feedbackTexts);
```

system prompt（buildSystemPrompt）追加一行约束：
"预期结果必须使用用户在页面上可感知的现象；编写 expected 时优先使用 userFeedbackTexts 对照表中的实际提示文案，禁止 HTTP 状态码/接口字段名/代码变量名。"

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 证据扫描漏报（MyBatis XML/Builder/字段直赋值等形态） | 漏报只导致"未校验"（不加标记不降级），不产生错误数据 |
| 层 2 文本断言误报失败（文案与 expected 措辞差异） | 关键词提取以连续中文段为主，toast 文案通常完整出现；失败信息带期望/实际全文供人工判断 |
| textSnippet 只有前 500 字符，长页面 toast 消失快 | 断言前不额外等待（点击类步骤已有 EFFECT_CHECK_DELAY_MS）；state_assert 步骤本身在操作之后，文本窗口覆盖主流场景；漏检时 failed 而非假通过——保守方向正确 |
| unverified 标记无前端展示 | 非目标，v7.8 随评审闭环处理 |
| A11 缓存与新字段的兼容 | userFeedbackTexts 是新字段，旧缓存无此字段时 get 返回 null → 空列表，自然兼容 |
