1. **准确率是核心价值**：对测试用例/分析结果正确性影响大的问题优先修，即使需要付出一定效率代价。

3. 优先选择"既提准确率又不伤效率（甚至提效率）"的方案。

## 一、LLM 组件问题（L 系列）

### L1【P0·速赢】流式取消是全局单例，并发生成互相干扰 ✅ v7.3 已修
- **位置**：`LlmService.java` L96-97（`activeStream` / `streamCancelled`）
- **问题**：只保存最后一个流。用户 A 取消时 dispose 掉用户 B 的流（B 抛 `GenerationCancelledException` 被误杀）；取消标志同样跨请求污染。
- **影响**：多用户并发生成时数据正确性事故，v4.2 多线程改造后遗留的单流假设。
- **修复思路**：改为 per-request 取消上下文（调用方传入取消信号，替代全局字段）。
- **权衡**：准确率收益高（正确性）；效率成本≈0（纯重构）。**先修。**

### L2【P1·速赢】熔断器全局共享且通道互相污染 ✅ v7.3 已修
- **位置**：`LlmCircuitBreaker.java`（LlmService 单实例持有）
- **问题**：① 文本（Spring AI）与多模态（MCP `llm_chat_with_image`）两通道共享熔断状态，任一故障连坐；② 401 等不可重试配置错误也计入失败，快速打满熔断 → 全系统 LLM 功能 503；③ PRD 解析/生成/评审/执行决策四种轻重任务无隔离。
- **修复思路**：按通道（text/multimodal）拆分熔断器实例；不可重试错误（4xx 配置类）不计入熔断计数。
- **权衡**：可靠性收益高；效率成本≈0。**先修。**

### L3【P2·速赢】thinking 开关是"幻觉配置"（背景已澄清）✅ v7.10 已修（诚实化）
- **位置**：`LlmService.java` L43-44（OpenAI starter 不透传 `enable_thinking`）
- **背景（用户确认 2026-08-22）**：v5.14 曾实际开启 thinking，因思考时间过长影响效率而主动降级关闭——**关闭本身是符合"效率优先于边际准确率"原则的正确决策**。
- **遗留问题**：降级后配置项/文档/设置界面仍以"可生效的开关"形态存在——用户打开开关会以为思考已启用（实际是 no-op），属于"未标记的降级"而非 bug。
- **修复思路**：保持关闭不动，只做诚实化——设置界面该选项标注"当前版本不生效（性能原因已降级）"或直接移除；避免误信。
- **长期（可选，随 A15）**：A15 的 PRD 解析内容 hash 缓存落地后，thinking 的耗时成本被缓存摊薄（每个 PRD 只付一次），可重新评估**仅对 PRD 解析开启** thinking（低频高价值场景）；生成链路（高频）保持关闭。
- **权衡**：诚实性修复；成本≈0。分区不变（速赢区，改 UI 标注即可）。
- **v7.10 落地**：配置诚实化——`LlmService` 启动时 warn 告知 thinking 三项为咨询性配置不生效（Spring AI OpenAI starter 无法透传 enable_thinking）；application.yml 与 .env.example 同步注释标注。长期项（随 A15 重评估 PRD 解析 thinking）维持延后。

### L4【P1·攻坚·分两步】PRD 截断策略系统性丢失尾部内容 ✅ L4a 已修（v7.7，L4b 延后）
- **位置**：`PrdAgent.java` L42-43（单文档 12000 / 总量 24000 字符**尾部硬截断**）
- **问题**：验收标准、边界条件、异常流通常在 PRD 后部，恰被丢弃。
- **修复思路（分两步）**：
  - 第一步 L4a（低成本）：截断改为"头部 + 尾部各保留一半"，覆盖后部关键内容；
  - 第二步 L4b（延后评估）：分段解析 + 汇总（增加 LLM 调用次数，接受可控成本）。
- **权衡**：L4a 准确率收益大、成本≈0，**先做**；L4b 随 A14 一起评估效率成本。

### L5【P0·速赢】SPA 页面有效性误判 → 重复提交表单 ✅ v7.3 已修（最小版）
- **位置**：`ExecutionAgent.java` L322-347（LLM 未配置/异常时退化为 URL 比较）
- **问题**：SPA URL 不变 → 几乎所有操作判为"未生效" → 触发 DOM 兜底再点一次 → **首次点击实际成功时造成重复下单/重复提交**。`alreadyDomClicked` 只防 DOM 路径重复，不防"视觉点击成功后再 DOM 点击"。
- **修复思路**：有效性对比从"URL/标题"改为"DOM 快照指纹（关键元素 hash）+ 截图对比"，零额外 LLM 调用。
- **权衡**：准确率收益极高（执行正确性）；效率成本≈0（本地计算）。**先修。**

### L6【P0·攻坚】structuredSteps 的 expected 从未被验证 ✅ 已修（v7.6）
- **位置**：执行闭环整体（生成侧有 expected 字段，执行侧无断言机制）
- **问题**："用例通过"≠"预期结果成立"，执行结果可信度被系统性高估——产品核心承诺的缺口。
- **修复思路**：执行每步后增加轻量断言：DOM 文本包含预期关键词 / 接口响应码 / 元素状态变化；断言失败标记步骤 FAILED 而非只看操作是否生效。
- **权衡**：准确率收益极大（核心可信度）；效率成本中等（每次执行多一次本地校验，无 LLM 调用）。**准确率优先，排攻坚首位。**

### L7【P1·延后】执行链路 LLM 调用无预算上限
- **问题**：每步最坏 4 次 LLM 调用 + 5 轮滚动截图定位，20 步用例最坏 100+ 次调用，无每用例/批次 token 预算。
- **修复思路**：按用例/批次设 token 与调用次数硬上限（配置化），超限降级为程序化模式。
- **权衡**：这是成本护栏而非准确率问题；实现简单可先加配置，完整预算统计往后放。

### L8【P1·速赢】流式 JSON 截断静默丢用例 ✅ v7.3 已修
- **位置**：`TestGeneratorAgent.java` L64-72（手写解析器 braceDepth 不归零时静默丢弃）；`LlmService.java` L393（maxTokens 16384 硬编码）

- **修复思路**：检测到 braceDepth 未归零时：① 记 warning 日志 + SSE 事件提示用户；② 尝试局部补全解析最后一条（闭合括号重试）。
- **权衡**：准确率收益高（防丢数据）；效率成本≈0。**先修。**

### L9【P2·延后】失败经验库自我强化偏差

- **权衡**：准确率收益中等；归因机制开发成本高。**往后放**（先修 L5 减少误报源头，再谈经验库质量）。

### L10【P2·延后】extractJsonObject 六处复制粘贴

### A4【P0·攻坚·分两步】LLM 增强看不全源码但输出被直接信任 ✅ a 步已修（v7.7，b 步延后）
- **位置**：`SpringAnalyzer.java` L573-601（collectSourceSnippets 总量 16000/每文件 1500，按文件名含 controller/service 排序）；L663-688（mergeSupplementalEndpoints 只做 method+path 去重即入库）
- **问题**：大项目 LLM 只见约 10 个文件片段，深层 Service 不在 prompt 里，但补充接口无源码存在性校验——看不全还要求"如实补充"，等于鼓励编造。
- **修复思路**：

- **权衡**：a 步准确率收益高、成本≈0；b 步效率成本 > 边际准确率收益，**往后放**。

### A13【P0·攻坚】大 PRD 解析失败阻断整个生成 ✅ v7.7 已修（瘦身重试版）

## 附录 A：全量改动影响评估（不含延后区，2026-08-22）

### A.1 拓扑层面：骨架不动

不新增组件、不替换任何 Agent/Skill/存储。三链路调用关系原样保留。拓扑变化仅 6 处小手术：
- **新增缓存层 ×3**：PRD 解析缓存（A15）、组件摘要缓存（A11）、错误→文案对照表（G20层3）
- **新增数据边 ×3**：RAG 切片→考点清单（G16）、评审建议→用例回写（R1）、执行断言→覆盖率（L6/E4）
- **移动的边 ×2**：索引维护移出生成热路径（G19）、证据存储换位置（R11）

### A.2 语义层面：数据流的三个根本属性变化

1. **从"单向流水"变成"闭环回路"（影响最大）**：执行真实断言→失败库（R13 治理）→下次生成避坑；评审建议→回写用例（R1）→追加去重口径；代码证据→状态机转换（A17）→覆盖率可信；错误文案表→生成上下文（G20）→expected 可断言。系统从"生成完就结束"变成"结果反哺生成"——产品形态级变化。
2. **从"尽力而为+静默降级"变成"诚实可观测"**：分析带 warnings（C1）、指标分计划/执行（R7）、状态有降级标记（G5）、假指标归零（R6）、执行故障不再记 passed（E3/E4）。数据流可信度属性整体翻转。
3. **从"不可复现"变成"可复现基线"**：A9 排序 + A15/A11 缓存 → 同一项目两次分析 LLM 输入一致。这也是闭环反馈生效的前提（不可复现的系统，反馈进来的是噪音）。

### A.3 上线后可感知变化（预期管理）

- **数字先变难看（度量校准，非质量下降）**：覆盖率会降（R3 收紧+R7 分离+G1 不误杀）；通过率会降（E3/E4/E6 诚实化暴露存量假通过）。建议对外说明"指标口径修正"。
- **生成引擎行为**：G16 考点清单变大 → 用例数趋增、轮次趋满；G17 每轮 prompt 变小对冲。净效果：生成时长可能略升，token 成本大致持平。
- **用户可感知行为变化仅两处**：批量执行超限被拒（E7）、推送与落库一致（G2）。

### A.4 全量同批的耦合风险（必须同批或有序）

1. **G2 + R1 必须同批**：R1 评审建议回写会再次制造"推送≠落库"——G2 不一起上等于白修。
2. **E4/E5 依赖 G20 层3（可弱依赖）**：expected 是 API 语言时执行断言空转；最小断言版可先行，对照表到位后断言质量才兑现。
3. **A15 先于 G7**：需求 ID 稳定化依赖解析缓存先存在。

### A.5 结论

全量改动对数据流安全，前提是按依赖序分三波：**①诚实化（指标+状态+可观测）→ ②闭环（回写+断言+反馈治理）→ ③精准投喂（过滤+清单+缓存）**。修复路线批次划分已按此顺序。
