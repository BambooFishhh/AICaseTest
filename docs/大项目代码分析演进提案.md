# 大项目代码分析演进提案

> 状态：提案（v8.x 候选主题） | 提出：2026-08-23（v7.13 讨论中确认落盘）
> 关联风险项：A4b（LLM 增强看不全源码）、本提案为其结构性正解
> 前置版本：v7.13（输入截断上限扩容，覆盖到"大项目"级别）

---

## 1. 背景与核心矛盾

### 1.1 全量快照模式的天花板

当前分析器 LLM 增强是"全量快照"模式：把源码片段一次性塞进一个 prompt。

该模式有两道硬天花板：

1. **物理天花板**：预算再大都有限。500+ 文件的巨型项目即使塞 1M 字符也装不下；v7.13 放大后（Spring 120k / Vue 96k / 总闸 300k）约覆盖 30-40 个 Java 文件或 20-30 个 Vue 组件——"大项目"级别，再往上无解。
2. **模型天花板**：LLM 超过 ~150k tokens 后中段内容注意力明显衰减（lost in the middle）——超出部分塞了也白塞，纯烧 token。

### 1.2 重复分析的成本矛盾

即使项目装得下，每次重新分析全量源码都重新过一遍 LLM：
- 分析是高频操作（每次进入分析流程触发）
- 大项目单次全量增强调用成本可观（源码上下文线性计费）
- 源码大部分没变，却重复付费

现有部分缓解：A11 组件摘要缓存（仅 VueAnalyzer 逐组件链路）、A15 PRD 解析缓存——SpringAnalyzer 全量增强链路无缓存。

### 1.3 已埋好的架构种子

本项目其实已验证过正确方向的组件，缺的是推广与整合：

| 现有资产 | 位置 | 在目标架构中的角色 |
|---|---|---|
| 逐组件语义摘要（完整读文件不截断） | VueAnalyzer v6.1 Agentic RAG | map 阶段的原型 |
| 组件摘要缓存（prompt hash 失效） | A11 / LlmResultCacheService | map 阶段的缓存层 |
| 源码优先级排序 | SpringAnalyzer.sourcePriority | 分批的排序基础 |
| 子集二次送评 | TestCaseReviewAgent R4 | "拆小批"的先例 |
| 并发 LLM 增强 | llm-concurrency:4 | 分批的并发基础 |
| Milvus RAG 切片管道 | v6.4 | 摘要检索的基础设施 |
| 按需求关键词过滤上下文 | G17 | 生成侧按需取用的先例 |

## 2. 三层递进方案

### 第 1 层：分批增强（Batched Enhancement）

**解决**：token 物理天花板。**改造量**：小。**定位**：大项目痛点出现时最先做的止血方案。

#### 设计

把 SpringAnalyzer 单次 `enhanceWithLlm` 改为按批次多次调用：

```
文件按 sourcePriority 排序（现有机制）
    → 切片成批（每批 ≤ spring-source-total-chars 预算）
    → 每批独立 LLM 调用（可走 llm-concurrency 并发）
    → 结果 append 合并（supplementalEndpoints 等本就是列表，合并天然无冲突）
```

#### 关键点

- **批内容 hash 缓存**：复用 A11 模式（LlmResultCacheService），批内文件集合与内容不变则缓存命中——源码局部修改时只有受影响的批次重新调用
- **A4a 校验按批汇聚**：knownClasses/knownPathPrefixes 取全量文件集合（与现状一致，不受分批影响）
- **失败隔离**：单批失败不影响其他批（现有 enhanceWithLlm 失败降级语义按批生效）
- **先例**：TestCaseReviewAgent R4 缺评子集二次送评、VueAnalyzer 逐组件并发——同一个"拆小批、可并发、可缓存"套路在 Spring 侧照抄

#### 预期收益

- 覆盖任意规模项目（批次数无上限）
- token 成本从"全量×每次"变为"全量×首次 + 增量×后续"

### 第 2 层：map-reduce 摘要（结构性正解）

**解决**：token 天花板 + 重复分析成本 + 增量更新。**改造量**：中。**定位**：长期正解，v8.x 主题候选。

#### 设计

把"原始源码当上下文"改为两阶段：

**Map 阶段（per-file 摘要）**：
- 每个源文件生成微摘要（300-500 字符）：职责 / 暴露接口 / 状态变更 / 校验规则 / 异常抛出
- 按文件内容 hash 缓存——**文件不变摘要永不重算**
- 摘要落库（新表 `source_summary`：projectId + file path + contentHash + summary + updatedAt）

**Reduce 阶段（增强调用）**：
- enhanceWithLlm 的 prompt 组装改为：摘要集（全部文件）+ 少量关键文件原文（Controller 给原文，Service/Utils 给摘要）
- prompt 体积从源码量级降到摘要量级（降一个数量级），且天然覆盖全项目

#### 关键点

- **增量分析免费获得**：重分析时只有 contentHash 变化的文件重新 map；reduce 阶段输入变化才重调——"重新分析大项目"从全量 LLM 变成增量 LLM
- **与 v7.13 的关系**：v7.13 放大的是 reduce 阶段可见的原文量；map-reduce 落地后这两个预算参数退化为"关键文件原文配额"
- **VueAnalyzer 顺带受益**：其逐组件摘要（v6.1）本身就是 map 阶段，补齐落库与 hash 失效即纳入同一体系
- **摘要质量保障**：摘要 prompt 明确"为端到端测试用例生成服务"，保留交互入口/接口契约/状态语义，丢弃实现细节

### 第 3 层：按需检索（生成侧配套）

**解决**：生成侧上下文精度（分析期不再追求 LLM 看过全部代码，生成期要什么取什么）。**改造量**：中。**定位**：与 map-reduce 天然配套，同版本或后续落地。

#### 设计

- 文件摘要进 Milvus（复用 v6.4 RAG 切片管道，新增 source-summary 类别）
- 生成用例时按当前需求语义检索最相关的源码摘要注入——G17 的"按需求关键词过滤"从静态产物（endpoints/rules）扩展到源码摘要资产
- 检索配额纳入 G9 分类别配额体系（新增 source 类别，如 4 条）

#### 关键点

- 与 G16（RAG 切片进考点清单）同构：检索回的摘要作为生成上下文，而非贴 prompt
- 解决"分析期一次快照无法预知生成期需要什么"的根本错配

## 3. 实施建议

### 3.1 触发条件（什么时候启动）

| 信号 | 对应层 |
|---|---|
| 真实项目文件数超出 v7.13 预算（分析质量随项目变大明显下降） | 第 1 层 |
| 大项目重新分析成本不可接受 / 频繁全量重分析 | 第 2 层 |
| 生成用例时上下文与需求错配（覆盖率缺口指向分析未见过的模块） | 第 3 层 |

**明确原则**：在上述信号出现前不启动——v7.13 的 300k 总闸对当前使用场景已足够，提前做是过度设计。

### 3.2 版本排布建议

```
v8.1  分批增强（第 1 层）          —— 止血，改造量小
v8.2  map-reduce 摘要（第 2 层）   —— 依赖 v8.1 的批缓存基建
v8.3  摘要检索（第 3 层）          —— 依赖 v8.2 的摘要资产
```

每层独立可交付、独立可回滚（配置开关：`app.analyzer.enhance-mode: snapshot | batched | mapreduce`）。

### 3.3 与现有风险清单的关系

- 本提案 = A4b（LLM 增强看不全源码但输出被直接信任）的结构性正解；A4a（补充接口源码校验）已修，其 knownClasses 闸门在分批模式下继续有效
- 第 2 层落地时同步消化 A16（表格型 PDF 提取质量差）的机会窗口：摘要层可对非代码文档做同样的 map 处理（低优先级，不绑定）

## 4. 开放问题（启动时需评审决策）

1. **摘要存储选型**：MySQL 新表 vs 复用 Milvus payload——倾向 MySQL（可事务、可审计）+ Milvus 只放向量
2. **map 并发预算**：大项目首扫 map 调用数 = 文件数，需评估限流与 llm-concurrency 配比
3. **摘要失效级联**：文件 A 依赖文件 B，B 的摘要变了 A 的 reduce 结果是否需要重算——倾向不做级联（reduce 输入含全量摘要，任何变化都会反映在下一次分析）
4. **与 G7（需求 ID 内容 hash）的对齐**：摘要 contentHash 采用同款 SHA-256 前 10 位方案，保持工程一致性
