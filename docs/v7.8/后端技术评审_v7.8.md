## 1. 现状与调用链

```
TestGeneratorAgent.generatePrdDrivenCases
  ├─ filterByFocusTypes / enrichStructuredSteps
  ├─ testCaseReviewAgent.review(result, checklist, "generation", r)   ← R1/R3 改造点
  │    ├─ ruleReview      （structuredSteps 空剔除 + coverageRefs 补全/mergeEndpointRefs）

  │    └─ applyEndpointMatching（matchEndpoint 收口）                ← R3 改造点

  ├─ deduplicate（保留 qualityScore 高者）
```

关键时序：**评审先于评分**（L771 → L778），G6 可直接读 hints.aiReview；R1 自动采纳发生在评审内，评分时已能看到"采纳后"状态。

## 2. R1 分级采纳 suggestedChanges

### 2.1 设计

`applyReview(TestCase tc, JsonNode reviewNode, String source)` 扩展：

```java
double confidence = reviewNode.path("confidence").asDouble(0.5);
Map<String, Object> suggestions = normalizeSuggestions(reviewNode.path("suggestedChanges"));
List<String> autoApplied = new ArrayList<>();
if (confidence >= 0.8) {
    // coverageRefs：并集合并（复用 R2 mergeCoverageRefs，只增不减）
    // priority：枚举校验 P0-P3 后 setPriority
}
review.put("autoApplied", autoApplied);
```

- 只处理 `coverageRefs` 与 `priority` 两类；`title/module/type` 不动
- `autoApplied` 登记 successful 应用的字段名
- 单用例 rerun 路径走同一 `review()` → 自动生效，无需单独处理
- 历史记录（AiReviewHistoryRecorder）在 review 之后调用，读到的是采纳后状态——符合"记录最终事实"语义

### 2.2 测试要点

- confidence 0.85 + refs 建议 → refs 并集 + autoApplied=["coverageRefs"]
- confidence 0.6 + refs 建议 → 不应用，autoApplied 为空
- priority "P0" 应用；"P9"/"高" 不应用
- coverageRefs 建议不删除既有 refs（与 R2 一致性回归）

## 3. R3 endpoint 匹配收紧

### 3.1 设计

`matchEndpoint` 重构为两级：

```java
private static final double FUZZY_THRESHOLD = 0.9;

private EndpointMatch matchEndpoint(Map<String, Object> ep, Map<String, Object> coverage) {
    // 第一遍：method 相同 + 归一化路径完全相等 → 精确匹配（fuzzy=false）
    // 第二遍：method 相同 + pathScore ≥ 0.9 + token 数一致 → 模糊匹配（fuzzy=true）
    // 都不中 → null
}
```

- 新增内部结果类型 `EndpointMatch {String id; boolean fuzzy;}`（私有静态内部类）
- `mergeEndpointRefs` 收集 fuzzy 命中 id 写入 `hints.fuzzyEndpointIds`（Set 去重、保序）
- 保留既有 `endpointIds` 主列表语义不变（下游 CoverageService/统计无感）

### 3.2 数值验证（旧 vs 新）

| 用例引用 | checklist 真实 | 旧逻辑 | 新逻辑 |
|---|---|---|---|
| POST /api/order/delete | POST /api/order/cancel | 0.667+0.2=0.867 匹配 ❌ | 0.667 < 0.9 不匹配 ✅ |
| POST /api/order/{id} | POST /api/order/* | 归一化相等匹配 | 精确匹配 ✅ |
| GET /api/user/list | GET /api/User/List/ | 0.75+0.2 匹配 | 归一化相等精确匹配 ✅ |
| POST /api/order/cancel | POST /api/order/cancel | 匹配 | 精确匹配 ✅ |
| POST /api/order/cancel | GET /api/order/cancel | 0.8+0=0.8 匹配 ❌ | method 不符不匹配 ✅ |

### 3.3 测试要点

- 上述表格全场景回归
- fuzzy 命中（构造 token 数一致、相似度 ≥ 0.9 的路径）→ fuzzyEndpointIds 有记录
- fuzzyEndpointIds 不污染 endpointIds 主列表语义（主列表仍含 fuzzy 命中的 id——覆盖统计口径不变，仅提示用途）

## 4. R7 计划/执行双栏覆盖率

### 4.1 设计

`getCoverageMatrix` 内层循环重构：

```java
for (TestCase tc : testCases) {
    // 计划覆盖：coverageRefs.transitionIds 引用（无论是否执行）
    // 执行覆盖：isExecuted(tc) 且（refs 引用 或 smRef 引用）
    // 旧口径 covered = planned ∪ 已执行 smRef 兜底（向后兼容，与 v7.2 PreparseTest 语义一致）
}
tran.put("covered", !legacyCoveringIds.isEmpty());   // 向后兼容 = 旧并集口径
tran.put("testCaseIds", legacyCoveringIds);
tran.put("planned", !plannedIds.isEmpty());
tran.put("plannedCaseIds", plannedIds);
tran.put("executed", !executedIds.isEmpty());
tran.put("executedCaseIds", executedIds);
```

- `smRefTransitionsByCase` 只在 `isExecuted` 时解析（现状保留）→ 兜底同时进旧口径与执行覆盖
- summary 增加 `plannedCoveredTransitions/plannedRate/executedCoveredTransitions/executedRate`；`coveredTransitions/rate` 保持旧并集口径

### 4.2 前端（CoverageMatrix.vue）

- 汇总：两条进度条（计划/执行），文案区分"计划覆盖"与"执行验证"
- 表格列：`计划覆盖` + `执行覆盖` 两列；行样式改为三态（executed 绿 / planned-only 黄 / 未覆盖红）
- `row.covered` 继续可用（兼容），新逻辑用 `row.planned` / `row.executed`

### 4.3 测试要点

- 未执行用例引用 → planned=true, executed=false
- passed 用例引用 → 两者 true
- failed 用例 smRef 引用（refs 为空）→ executed=true, planned=false（兜底只进执行列）
- summary 四字段口径 + 兼容字段不破坏

## 5. G6 质量评分并入评审结论

### 5.1 设计

```java
private int calculateQualityScore(TestCase tc) {
    int formScore = calculateFormScore(tc);            // 原 6 项检查，0-100
    Map<String, Object> hints = JsonHelper.parseMap(tc.getExecutionHints());
    int reviewScore = reviewScoreOf(hints);            // 0-30
    int penalty = uiLanguagePenaltyOf(hints);          // 0-9
    return Math.max(0, Math.min(100, (int) Math.round(formScore * 0.7) + reviewScore - penalty));
}

private int reviewScoreOf(Map<String, Object> hints) {
    Object reviewObj = hints.get("aiReview");
    if (!(reviewObj instanceof Map)) return 15;        // 无评审 → 中性
    // pass → 30；fix → 30 - issues*5 - 未采纳建议*5（下限 0）
    // confidence < 0.5 → 减半
}
```

- "未采纳建议" = suggestedChanges 中非 null 且不在 autoApplied 中的字段数（R1 联动：自动采纳后不罚）
- `uiLanguageViolations` 每项 −3，上限 −9（与 v7.3 lint 标记联动）
- 评分入口只此一处，`SemanticService.deduplicateBatch` 读同一字段自动受益

### 5.2 测试要点

- 同形式分：pass(30) > fix(1 issue, 20) > fix(3 issues, 0) = 无评审(15)+形式分差
- confidence 0.4 的 fix → 评审分减半
- autoApplied 后建议不计扣分
- uiLanguageViolations 2 项 → −6；5 项 → −9（封顶）
- 无 aiReview 的用例（历史数据）→ 形式分 × 0.7 + 15，不抛异常

## 7. 回滚方案

- R1：autoApplied 为纯增量字段，回滚 = 删除采纳分支
- R3：阈值/精确匹配为新逻辑，回滚 = 恢复旧 matchEndpoint；fuzzyEndpointIds 无下游依赖
- R7：兼容字段保留，回滚 = 前端隐藏执行列即可（后端新增字段无害）
- G6：评分公式集中在 calculateQualityScore 一处，回滚 = 恢复原公式
