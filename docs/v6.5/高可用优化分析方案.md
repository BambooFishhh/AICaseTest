# 高可用优化分析方案（完整版）

> 适用系统：AICaseTest Agent 主流程（分析 → 生成 → 执行 → 回归）。
> 目标：进程崩溃、机器重启、LLM 异常、下游工具失败、网络抖动等场景下，任务不丢失、可恢复、可降级，避免任务直接报废。
> 基线：v6.5 已落地 P0 基础（agent_task 持久化、租约恢复、管理端重试、LLM 重试分类），本方案面向完整演进。

## 0. 现状与核心缺口

### 已具备

- 有界线程池：analysis/generation/execution/semantic 四池分离，参数可配，详见 [AsyncConfig.java](backend/src/main/java/com/testagent/config/AsyncConfig.java:83)。
- 运行态：Redis/内存 RuntimeStore（取消标志、心跳、并发配额）。
- v6.5 `agent_task`：分析/生成/追加生成写入任务状态机，phase/checkpoint/attempt/lease 持久化，启动恢复将租约过期任务标记 `NEEDS_REVIEW`，详见 [AgentTaskService.java](backend/src/main/java/com/testagent/service/AgentTaskService.java:29)。
- LLM 重试分类：超时/网络/429/5xx 重试，4xx 与未知错误立即失败，延迟加抖动，详见 [LlmRetryPolicy.java](backend/src/main/java/com/testagent/common/LlmRetryPolicy.java:10)。
- 执行链路：逐步骤失败不中断、Agent 视觉定位失败降级 DOM/规则策略，详见 [ExecutionAgent.java](backend/src/main/java/com/testagent/agent/ExecutionAgent.java:176)。
- 可观测：Telemetry 分阶段落库、Prometheus 指标、Grafana 面板、traceId 日志。

### 核心缺口

1. `McpConnection.sendRequest` 的 `future.get()` 无超时，下游工具挂起会让任务永久卡 RUNNING，详见 [McpConnection.java](backend/src/main/java/com/testagent/mcp/McpConnection.java:319)。
2. 恢复语义偏保守：只标记 `NEEDS_REVIEW`，没有 checkpoint 续跑；执行任务尚未接入 `agent_task`。
3. `TaskQueueService.recoverStaleTasks` 仍直接清空内存/Redis 队列计数，见 [TaskQueueService.java](backend/src/main/java/com/testagent/service/TaskQueueService.java:37)，队列不是可靠消息载体。
4. 线程池拒绝策略为 `CallerRunsPolicy`，高负载会倒灌 HTTP 线程，见 [AsyncConfig.java](backend/src/main/java/com/testagent/config/AsyncConfig.java:89)。
5. `analysisRunning`、`cancellationFlags` 等仍以本地 Map 为准，多实例不共享。
6. 无整体任务 TTL、无 LLM/工具熔断、无自动续跑、无前端任务中心。

## 1. 任务与状态持久化、状态机、checkpoint、幂等

### 1.1 agent_task 状态机

状态集：`CREATED → QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELLED / NEEDS_REVIEW / DLQ`。

按任务类型定义阶段：

| 任务类型 | 阶段 |
|---|---|
| analysis | scan → parse → state_machine → index |
| generation | validate → generate → persist → index |
| append_generation | validate → generate → persist(追加) → index |
| execution（P1 接入） | claim → browser_launch → step{N} → record → report |

规则：

- 每个阶段进入前先写库（write-ahead），再执行外部动作。
- `checkpoint_json` 只存可序列化的断点元数据，不存 SSE 连接、浏览器会话等进程内对象。
- 状态迁移幂等：同一 taskId 重复 `succeed`/`fail` 不改变已终态。
- 只有 lease 过期的 `RUNNING` 才允许恢复，防止双 worker 同时执行。

### 1.2 checkpoint 断点续跑设计

#### 分析

- 已完成 `frontend_result` / `backend_result` 写入 `code_analysis` 后，checkpoint 到 `parse_done`。
- 状态机提取、语义索引可幂等重建，重启后可从 `state_machine` 阶段续跑。

#### 生成

- 生成多轮输出先缓存到 checkpoint JSON，按模块记录 `module -> caseSnapshots`。
- `replaceAll` 是破坏性副作用：必须在执行前记录 `persist_started`，执行完成后记录 `persist_done`；续跑时若 `persist_done` 已存在，禁止再次 replaceAll，直接重建索引。
- 部分成功策略：LLM 完成模块 A、模块 B 失败，若 A 的 checkpoint 已落盘，允许"生成侧从 B 继续 + 落库时只补更增量"，否则回落人工复核。

#### 执行

- 每个 `ExecutionStep` 独立落库即天然 checkpoint：重启后从最后已提交步骤的下一个步骤重试；浏览器会话不可持久化，重试时重开浏览器。
- 无法重开的副作用（点击、提交）不自动重试，标记 `NEEDS_REVIEW`。

### 1.3 幂等性设计

| 副作用 | 幂等方案 |
|---|---|
| 创建任务 | `request_id + task_type` 唯一，活跃状态复用，v6.5 已实现 |
| 生成落库 | `replaceAll` 前写 `persist_started`，完成后写 `persist_done`，续跑比较快照指纹 |
| 语义索引 | 先按 project 清集合再写，天然幂等；追加模式用 caseId 去重 |
| 执行 | 单用例 running 去重沿用；lease 恢复后由人工确认或从步骤断点重试 |
| 工具调用 | 幂等工具（截图/状态/滚动）可自动重试；非幂等（点击/输入/提交）默认不自动重试 |

## 2. 中断场景容错

### 2.1 LLM 调用异常

已实现：

- 重试分类 + 抖动：`LlmRetryPolicy`。
- 重试次数可配：`LLM_RETRY_MAX_ATTEMPTS`。

待补：

| 能力 | 设计 |
|---|---|
| 单次调用总超时 | 每次调用给定 deadline（默认 3 min），超时抛可重试错误；并发总预算 ≤ maxRetries |
| 任务级 TTL | 生成/分析任务最长 60 min，到期强制 NEEDS_REVIEW，防 LLM 无限挂起 |
| 熔断 | 按 provider 计数：10 次窗口内失败率 > 50% 短路 30s，期间任务转队列或规则降级 |
| 流式重试边界 | 首 token 前失败可整体重试；首 token 后失败视为"效果未知"，不重复推流，任务人工复核 |
| 模型拒绝 | 4xx/校验错误不重试，直接 FAILED + 错误码，便于前端给出语义化提示 |

### 2.2 外部工具调用故障（MCP/Playwright）

当前缺陷：`future.get()` 无超时。

设计：

- 每工具超时：browser 默认 60s、tools 默认 30s、llm vision 默认 90s，配置化。
- 工具错误分类：`TOOL_TIMEOUT`、`TOOL_NOT_FOUND`、`TOOL_SESSION_LOST`、`TOOL_ILLEGAL_ARGS`、`TOOL_UNKNOWN`。
- 重试策略：只有幂等工具自动重试 1 次；会话丢失重启浏览器 1 次后仍未恢复 → `NEEDS_REVIEW`。
- 子进程健康：定时 ping、进程退出检测、异常退出自动拉起最多 2 次，仍失败进入降级路径。

### 2.3 进程 OOM / 被杀 / 机器重启

- 保留已有优雅停机（shutdown graceful + 30s 等待）。
- JVM：加入 heap 使用率/GC 耗时指标；达到阈值拒绝新任务而非 OOM-kill。
- 恢复：启动时按 `agent_task` lease 恢复（v6.5 已标记 NEEDS_REVIEW）；P1 只对 checkpoint 安全的阶段自动续跑。
- 执行：接入 `agent_task` 后，重启把 running 执行标记 failed/NEEDS_REVIEW，步骤从最后已提交 step 续跑。
- 数据保护：执行证据按 step 先落盘再更新 DB，避免"报告有记录但文件缺失"。

### 2.4 网络抖动

- 已配置 HTTP connect/read timeout；增加 retry + jitter（有限次数）。
- SSE：保留 ticket 机制；前端断线分两类：
  - 显式取消 → `CANCELLED`；
  - 网络抖动断线 → 服务端继续执行，前端按 `GET /api/projects/{id}/tasks/active` 重连并补拉进度。
- 幂等查询接口：任务详情/状态接口供前端轮询，SSE 只做增量通知。

## 3. 降级兜底机制

### 3.1 自动重试降级链

```
LLM 正常 → LLM 重试 2~3 次 → 规则兜底生成（confidence 低 + degraded=true）→ 任务 NEEDS_REVIEW
Agent 视觉定位失败 → DOM 定位 → 按可访问文案/URL 对比 → step 失败但不中断批次
Milvus 不可用 → 跳过语义检索，只注入关键词命中 → 记录 degraded
Redis 不可用 → RuntimeStore 切内存（单实例可用）→ 写入 degraded 告警
```

### 3.2 部分结果返回

- 生成：分模块成功即持久化部分模块，任务标记 `degraded=true`，complete 事件带 `partial=true`。
- 追加生成：现有逻辑已是增量，继续保留。
- 分析：前端分析与后端分析独立，单个失败保留另一个结果。
- 执行：批次级失败仅影响单个用例，报告保留已执行步骤证据。

### 3.3 人工兜底

- `NEEDS_REVIEW` + `DLQ` 状态已在 v6.5 预留。
- 管理端列表/详情/重试已实现；P1 增加前端任务中心：状态筛选、error/checkpoint 查看、确认后重试。
- 重试前展示"将覆盖旧结果/只追加/从断点续跑"三种语义，避免误操作。

### 3.4 防无限循环

| 防护 | 现值/目标 |
|---|---|
| 生成轮数上限 | 已有 `MAX_GENERATION_ROUNDS=4` |
| 每任务尝试次数 | `max_attempts`（v6.5 字段，默认 3） |
| 每阶段重试次数 | LLM 3 次、工具幂等 1 次 |
| 元素滚动兜底 | 现有 5 次上限 |
| 任务级 TTL | P1 增加（分析/生成 60min、执行 30min） |
| DLQ | 超限自动转 DLQ，不再执行 |

## 4. 并发与故障隔离

### 4.1 队列设计

演进路线：

1. 现状：线程池 + Redis Set 计数 + HTTP 触发 @Async。
2. P1：DB `agent_task` 为事实源，`QUEUED` 由调度器轮询/Redis Stream 驱动；HTTP 只负责入队并返回 taskId。
3. P2：Redis Streams consumer groups：

```
队列：aicasetest:task:analysis / generation / execution
生产者：HTTP 入队 XADD（payload=taskId）
消费者：worker XREADGROUP 领取 → claim → 执行 → XACK
失败：XPENDING 检查 → AUTO_CLAIM 超时重领 → 超次数转 DLQ
```

### 4.2 死信队列

- `agent_task.status=DLQ` 为最终事实源，管理端可 requeue。
- Redis DLQ stream 只做告警节奏控制，不以它作为唯一真相。
- DLQ 告警：长度 > 0 即 page：错误码聚合、首次出现时间、任务链接。

### 4.3 资源隔离

- 四池分离保持；把 `CallerRunsPolicy` 改为拒绝后落库 `QUEUED` + 返回 202，由调度器消化。
- 项目级并发：分析 1、生成 1、执行 N（沿用 ProjectExecutionLimiter）。
- LLM 并发：使用 `EXECUTOR_LLM_CONCURRENCY`，按 provider 做令牌桶，避免单账号限流拖垮全站。
- 数据库连接池：Hikari 已调优；任务 checkpoint 高频写库需监控慢查询。

### 4.4 多实例要点

- DB lease（v6.5 字段）或 Redis `SET NX EX` claim，二选一，杜绝本地 Map 当事实源。
- 取消标志、心跳、配额全走 Redis RuntimeStore。
- 调度器需幂等：`claim` 用 CAS 条件更新（`status=RUNNING AND lease_expire_at < now`）。
- 单实例降级：Redis 不可用时只允许单实例模式，禁止多实例内存态互相覆盖。

| 指标 | 含义 |
|---|---|
| `aicasetest.task.started/completed/failed/retried/degraded` | 任务生命周期计数，按 task_type/status 标签 |

| `aicasetest.task.dlq_depth` | DLQ 当前数量 |

### 5.3 告警

Grafana 规则：

- 任务失败率 10 分钟窗口 > 20%
- LLM 重试率异常升高 / 连续 429
- `RUNNING` 且 heartbeat 超过 lease 未更新
- 队列深度 > 池容量 80%
- DLQ > 0
- 健康检查连续失败 3 次

### 5.4 任务回溯

- `agent_task` 记录 phase/checkpoint/attempt/error，已可支撑基础回溯。
- P2 增加 timeline：`checkpoint_json` 每次更新附加 `{ts, phase, summary}`，管理端按时间线回放。
- 与 `task_telemetry` 关联：按 `task_id` 关联 phase 耗时/token，形成单任务报告。

## 7. 高频踩坑点

1. 只加状态不落 checkpoint/payload：重启后仍然不知道从哪继续。
2. 恢复时"清空队列"会吞任务：应标记 NEEDS_REVIEW 或按断点续跑，而不是删除。
3. `replaceAll` 不具备天然幂等：崩溃后自动重跑会覆盖人工修改的用例，必须写 `persist_done` 断点。
4. 非幂等工具自动重试会重复点击/重复下单：点击、输入只允许人工确认重试。
5. 把 SSE 断线当成任务失败：前端断线 ≠ 任务中断；任务事实源必须是数据库状态机。
6. 对所有异常都重试：4xx/模型拒绝反复消耗额度，应分类后快速失败。
7. `CallerRunsPolicy` 会把压力倒灌 HTTP 线程：高负载应落库排队的背压。
8. 本地 Map 作为多实例事实源：`analysisRunning`、`cancellationFlags` 必须迁 Redis 或由 agent_task 承担。
9. 心跳和 lease 混淆：心跳=存活，lease=执行资格；恢复只能由 lease 过期触发。
10. 恢复与手动操作并发：同一任务被两个 worker/管理员同时操作，必须 CAS。
11. 观测只记录结束状态：进程被杀时 finish 不执行，必须阶段级写库才有回溯能力。
12. 内存 RuntimeStore 不是生产兜底：Redis 降级只允许单实例，禁止多实例共享内存态。
13. 没有故障注入演练：改造后不测 kill -9/断网/工具挂起，等于没验证。
