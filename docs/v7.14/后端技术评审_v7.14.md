## 2. buildCoverageChecklist 摘要化（G24）

现状（159KB 冗余源头）：

```java
Map<String, Object> item = new LinkedHashMap<>();
item.put("id", (ep.getMethod() == null ? "" : ep.getMethod().toUpperCase()) + " " + ep.getPath());
item.putAll(ep.toContextMap());          // ← requestBody/responseBody/businessLogic/... 全量塞入
endpoints.add(item);
```

修改后：

```java
// v7.14(G24): 覆盖清单只放对账标识字段——完整详情已在 context.endpoints 注入过一次，
// putAll(toContextMap()) 等于把 220 接口全量详情重复灌进 prompt（实测 159KB 冗余）。
// 消费方核实：remainingGaps/TestCaseReviewAgent 只读 id/method/path。
Map<String, Object> item = new LinkedHashMap<>();
item.put("id", (ep.getMethod() == null ? "" : ep.getMethod().toUpperCase()) + " " + ep.getPath());
item.put("method", ep.getMethod());
item.put("path", ep.getPath());
item.put("function", ep.getFunction());
endpoints.add(item);
```

同构处理：

```java
// rules：{id, ruleType, rule 截 80}——全文在 context.businessRules（top-100 完整）
Map<String, Object> item = new LinkedHashMap<>();
item.put("id", "rule-" + i++);
item.put("ruleType", br.getRuleType());
item.put("rule", truncate(br.getRule(), 80));
rules.add(item);

// dependencies：{id}（= operation 全名，依赖对账键；dependsOn 明细不进清单）
Map<String, Object> item = new LinkedHashMap<>();
item.put("id", od.getOperation());
dependencies.add(item);

// components：{id, component, summary 截 80}——完整 map 在 context.frontendComponents
Map<String, Object> item = new LinkedHashMap<>();
item.put("id", c.getOrDefault("id", ""));
item.put("component", c.getOrDefault("component", ""));
item.put("summary", truncate(String.valueOf(c.getOrDefault("summary", "")), 80));

```

requirements/transitions **不动**（无重复注入；G4 兜底匹配依赖 requirements 的 title/description）。

`truncate` 复用类内既有方法（若签名不符则加 null 安全包装：null → ""）。

## 3. context 容量控制（G25）

`generatePrdRound` 中 G17 过滤后追加：

```java
// v7.14(G25): G17 弱过滤（>0 即过，宁多勿丢）后加总量控制层——大项目 220 接口全放行时
// 全量详情 128KB 灌 prompt。按相关性降序保留 top-N，未入选接口仍在 coverageChecklist
// 摘要中可引用（id/method/path/function），只是无 request schema 详情。
relevantEps = capEndpointsByRelevance(relevantEps, keywordText);
relevantRules = capRulesByRelevance(relevantRules, keywordText);
```

实现（包级可见供单测）：

```java
@Value("${app.generation.endpoints-context-max:80}")
private int endpointsContextMax = 80;

@Value("${app.generation.rules-context-max:100}")
private int rulesContextMax = 100;

List<EndpointInfo> capEndpointsByRelevance(List<EndpointInfo> eps, String keywordText) {
    if (eps.size() <= endpointsContextMax) {
        return eps;
    }
    List<EndpointInfo> sorted = new ArrayList<>(eps);
    if (keywordText != null && !keywordText.isBlank()) {
        sorted.sort(Comparator.comparingInt(
                (EndpointInfo ep) -> scoreTextOverlap(endpointText(ep), keywordText)).reversed());
    }
    List<EndpointInfo> capped = new ArrayList<>(sorted.subList(0, endpointsContextMax));
    log.info("[G25] context endpoints capped: {}/{} (top by relevance, rest in checklist summary)",
            capped.size(), eps.size());
    return capped;
}
```

说明条目（注入 context 时追加，与 G10 checklist 截断说明同款模式）：

```java
if (relevantEps.size() < eps总原始数) {
    Map<String, Object> note = new LinkedHashMap<>();
    note.put("note", "endpoints 已按需求相关性保留前 " + relevantEps.size()
            + " 条完整详情，其余接口见 coverageChecklist.endpoints 摘要");
    epList.add(note);
}
```

rules 同构（`capRulesByRelevance`，ruleText 打分）。`List.sort` 稳定排序保证同分项按原序——确定性。

排序稳定性说明：`Comparator.comparingInt(...).reversed()` 配合 `List.sort`（TimSort，稳定）——同分条目保持原始顺序，同输入同输出。

## 5. embedding 端点修正（E17）

`application.yml`：

```yaml
spring.ai.openai.embedding:
  api-key: ${LLM_EMBEDDING_API_KEY:${DASHSCOPE_API_KEY:${LLM_API_KEY:}}}
  # v7.14(E17): 默认端点改 DashScope 兼容模式——原默认回落 chat 网关(opencode.ai/zen/go/v1)，

  base-url: ${LLM_EMBEDDING_BASE_URL:https://dashscope.aliyuncs.com/compatible-mode/v1}

  embedding-model: ${LLM_EMBEDDING_MODEL:text-embedding-v4}
```
