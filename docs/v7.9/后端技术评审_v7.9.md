## 2. 方案设计

### 2.1 E6：生效判断两级化

```java
private boolean askLlmIfEffective(Map<String, String> statusBefore, Map<String, String> statusAfter, String action) {
    // 第一级：本地三指纹比较（零成本）。变化即生效，省一次 LLM 调用。
    boolean changed = pageChanged(statusBefore, statusAfter);
    if (!llmService.isConfigured()) {
        return changed;   // 原兜底行为
    }
    if (changed) {
        return true;      // v7.9(E6): 指纹已变化，无需 LLM 复核
    }
    // 第二级：指纹无变化（SPA 局部更新存疑）→ LLM 终审，prompt 明示事实
    ...（现有 LLM 调用，userPrompt 前加"页面文本快照无变化"事实）
}
```

**要点**：
- 收益集中在常见成功路径（页面有变化）：每点击步骤省 1 次 LLM 调用（EFFECT_CHECK_DELAY_MS 后立即返回）。
- 指纹无变化时 LLM 输入与本地证据一致，维持"保守判未生效→DOM 兜底"既有语义；prompt 补充"文本快照无变化"提示降低 LLM 幻觉式"生效"。
- 不改 `pageChanged`、不改 DOM 兜底/alreadyDomClicked 保护。

### 2.2 E7：批量入口限流 + 排队超时

**入口限流**（`executeBatch`/`copyExecute` 开头）：

```java
private static final int MAX_BATCH_SIZE = 100;
if (caseIds == null || caseIds.isEmpty()) throw new IllegalArgumentException("...");
if (caseIds.size() > MAX_BATCH_SIZE) {
    throw new BusinessException(50013, "单批执行用例数超过上限 " + MAX_BATCH_SIZE + "，请分批执行", HttpStatus.BAD_REQUEST);
}
```

常量不做成配置（100 为工程经验值，避免配置面膨胀；后续有需求再提）。

**排队超时**（`RuntimeStore` 接口新增默认方法，双实现覆盖）：

```java
// RuntimeStore.java
default boolean tryAcquireProjectPermit(String projectId, int maxPermits, long timeoutMs) {
    acquireProjectPermit(projectId, maxPermits);  // 默认无限等待（旧行为）
    return true;
}

// MemoryRuntimeStore：semaphore.tryAcquire(timeoutMs, MILLISECONDS)
// RedisRuntimeStore：循环加 deadline，超时 return false（中断语义保留）
```

`ProjectExecutionLimiter` 增加 `tryAcquire(projectId, timeoutMs)`；`runAgentAsync`/`runAsync` 调用处：

```java
long timeoutMs = acquireTimeoutMinutes > 0 ? acquireTimeoutMinutes * 60_000L : 0;
if (timeoutMs > 0 ? !projectExecutionLimiter.tryAcquire(projectId, timeoutMs)
                  : (projectExecutionLimiter.acquire(projectId), false)) { ... }
```

实现上更简洁的写法：limiter 统一暴露 `acquireOrTimeout(projectId)`（内部读配置），超时抛 `BusinessException` → 现有 catch 收尾路径记 failed。配置 `app.executor.project-acquire-timeout-minutes`，默认 30；≤0 禁用（走旧 acquire）。

**超时后的收尾**：复用"启动前已取消"分支的收尾结构——记录 failed + endTime + summary"项目执行并发排队超时"，释放无需（未获得许可），agent_task 标 failed。

### 2.3 E9：ID 加长

统一抽私有方法（两文件各自就近）：

```java
private static String shortId() {  // v7.9(E9): 8→16 位，32bit→64bit 消除碰撞
    return UUID.randomUUID().toString().replace("-", "").substring(0, 16);
}
```

替换点：
- `ExecutionService.execute` L114：`executionId`（同时是 agent_task taskId，String 兼容）
- `ExecutionService.executeBatch` L186：`"batch-" + shortId()`
- `ExecutionService.copyExecute` L203：`"copy-" + shortId()`
- `ExecutionAgent` 两处步骤 ID（L265、L295）

注意 `substring(0, 8)` 原实现取自含连字符 UUID 的前 8 位（无连字符落在前 8 位，等价十六进制）。加长到 16 位同样落在第一段（8-4-4...，前 18 位才到第二个连字符），直接 substring 安全；为稳妥仍用 replace("-","") 后截取。

## 4. 兼容性与风险

- **E6**：行为变化仅"少调 LLM"（结果等价：指纹变化时旧版 LLM 输入相同证据，结论几乎恒为生效）。风险低。
- **E7**：入口限流是计划内可感知变化；排队超时默认 30min 远大于正常排队时长。`tryAcquireProjectPermit` 以默认方法形式加入接口，Redis 实现超时后返回 false（不再无限自旋），中断语义保留。
- **E9**：String 主键，新旧 ID 共存；前端展示/查询不受长度影响（无定长校验）。
- **E10**：默认 false，零行为变化。
- **R11**：仅可见化，不改存储；docker-compose 单机挂载已存在，多实例共享卷写入部署文档。
