## 二、运行态状态源核对

| 状态 | 存储 | 双实例行为 |
|---|---|---|
| 项目 analyzing/generating 进度 | MySQL（project 表 + agent_task 租约/checkpoint） | ✅ DB 权威，重启由 recoverStaleTasks 复位 |
| 取消标志 / 心跳 / 配额信号 | RuntimeStore（Redis 实现，APP_REDIS_ENABLED=true 时；内存实现仅限单实例） | ✅ Redis 下跨实例一致；⚠️ 内存实现双实例不共享（部署约束，见 §5） |
| 登录防爆破计数 | RuntimeStore 同上 | 同上 |
| LLM 结果缓存 | LlmResultCacheService——DB 表 llm_result_cache 为权威存储，内存为加速层 | ✅ 双实例安全（缓存 miss 仅多一次计算，无一致性风险）；Redis 未参与该缓存（设计如此，无需变更） |
| 执行截图/录屏证据 | 实例本地 outputs/ | ⚠️ 多实例需共享卷（v7.9 R11 已显式告警占位，不静默缺图） |

## 三、调度幂等性核对

- 补偿重放：按行认领后逐条重放，ShedLock 保证同刻单实例执行；失败退避由 attempts/next_attempt_at 驱动，重复触发安全。
- 对账：修复动作幂等（补索引=按 id 重写、孤儿删除按 id 删），报告行每次生成新 id 不冲突。
- TTL/租约恢复：CAS 式状态迁移（agent_task 终态守卫 E14），重复执行无害。
- 兜底分发：QUEUED 领取为 CAS 幂等（v6.8）。

## 四、结论

四项既有定时任务补齐 ShedLock 后，任务调度层具备双实例安全性。数据权威源均在 DB/Redis。

## 五、遗留限制（部署文档口径，非代码缺陷）

1. **RuntimeStore 必须启用 Redis 实现**（APP_REDIS_ENABLED=true）：内存实现的双实例取消/配额/防爆破互不可见。
2. **outputs/ 证据目录需共享卷**（NFS/云盘）或接入对象存储，否则报告缺图告警占位会频繁出现。

## 六、验证建议

本地双实例演练：不同端口起两实例（同一 MySQL/Redis），观察：
- 同一 cron 周期内恢复/TTL/对账日志只出现在一个实例（shedlock 表 locked_by 区分）；
- 实例 A 触发生成、实例 B 查询进度正常；
- 补偿表注入 PENDING 记录后仅一个实例重放成功置 DONE。
