# AICaseTest 本地代码审查修改方案

**文档日期**：2026-08-20  
**基线说明**：基于当前本地代码现状审查，不含实际代码修改。  
**目标**：在不破坏现有分析/生成/执行闭环的前提下，补齐安全预期、业务口径一致性和工程健壮性。

---

## 1. 审查结论概览

当前代码已经实现了 AICaseTest 的核心闭环：

- 项目分析、SSE 流式进度、生成/执行链路可用；
- 项目访问控制、登录失败锁定、生产环境安全开关已落地；
- URL 抓取加入了 SSRF 基础防护；
- 前端对 SSE、轮询和页面卸载清理做了基本收口。

但从“是否完全实现预期”角度看，仍有几处需要优先整改：

1. **首次登录未强制改密**，与项目预期不一致；
2. **SSE 使用 query string 携带 JWT**，存在泄露风险；
3. **`businessScore` 判定口径不一致**，会把通用组件漏进生成链路；
4. **项目列表访问控制存在 N+1**，数据量上来后会退化；
5. **Telemetry 的 ThreadLocal 清理不完整**，长期运行存在脏状态/内存滞留风险。

---

## 2. 必须修的问题（P1 / P2）

### 2.1 首次登录未强制改密

**严重度**：P1  
**影响范围**：安全 / 登录流程 / 前端入口控制

**相关文件**：
- `E:\java_project\AICaseTest\backend\src\main\java\com\testagent\config\DataInitializer.java:54-63`
- `E:\java_project\AICaseTest\backend\src\main\java\com\testagent\service\AuthService.java:68-81`
- `E:\java_project\AICaseTest\backend\src\main\java\com\testagent\entity\User.java:33-34`
- `E:\java_project\AICaseTest\frontend\src\App.vue:112-125, 189, 199, 234-239`

**问题描述**：
默认管理员账号 `admin/admin123` 会被初始化出来，但系统没有“首次登录必须修改密码”的状态位和强制拦截逻辑。前端虽然提供了“修改密码”弹窗，但属于手动操作，不是强制流程。

**触发场景**：
首次使用默认管理员登录后，用户可以继续访问系统主功能，不会被强制改密。

**整改方案**：
- 在 `User` 增加 `mustChangePassword` 或 `passwordExpired` 字段；
- `DataInitializer` 初始化默认 admin 时置为 `true`；
- 登录成功后通过 `/api/auth/me` 或登录响应返回该状态；
- 前端登录后如果标记为 true，强制弹出改密对话框并阻断主功能页面；
- 修改成功后清除标记。

**验收标准**：
- 默认管理员第一次登录后必须改密，否则不能继续使用系统；
- 改密后可正常进入主流程；
- 相关逻辑有后端单测 + 前端联动验证。

### 2.2 SSE 通过 URL query 传 JWT，存在泄露风险

**严重度**：P2  
**影响范围**：SSE 鉴权 / 安全

**相关文件**：
- `E:\java_project\AICaseTest\backend\src\main\java\com\testagent\security\JwtAuthFilter.java:34-56`
- `E:\java_project\AICaseTest\frontend\src\api\testcase.js:52-58`
- `E:\java_project\AICaseTest\frontend\src\views\ProjectDetail.vue:392-393`

**问题描述**：
为兼容 `EventSource`，前端把 token 拼到 URL 上，后端也支持 `?token=` 认证。这样虽然功能可用，但 token 会暴露在浏览器历史、代理日志、访问日志等位置。

**触发场景**：
只要打开分析流或生成流 SSE，请求 URL 中就会携带 token。

**整改方案**：
优先级建议如下：
1. **优先方案**：单独增加一个短期 SSE ticket 接口，先走普通 JWT，再换一次性票据；
2. **次优方案**：改成 HttpOnly Cookie 鉴权；
3. **临时方案**：保持 query token，但必须做超短 TTL、一次性使用、日志脱敏。

**验收标准**：
- 正常 SSE 仍可使用；
- 请求 URL 中不再出现长期有效 JWT；
- 日志、浏览器历史、监控链路中不泄露真实 token。

### 2.3 `businessScore` 过滤口径不一致，通用组件会漏进覆盖清单

**严重度**：P2  
**影响范围**：组件筛选 / LLM 调用 / 生成结果质量

**相关文件**：
- `E:\java_project\AICaseTest\backend\src\main\java\com\testagent\analyzer\VueAnalyzer.java:941-955`
- `E:\java_project\AICaseTest\backend\src\main\java\com\testagent\analyzer\VueAnalyzer.java:1125-1159`
- `E:\java_project\AICaseTest\backend\src\main\java\com\testagent\agent\TestGeneratorAgent.java:471-476`
- `E:\java_project\AICaseTest\backend\src\main\java\com\testagent\agent\TestGeneratorAgent.java:1291-1302`

**问题描述**：
- `VueAnalyzer` 中“是否业务组件”的阈值是 `>= 0.3`；
- `TestGeneratorAgent.filterBusinessComponents()` 却使用 `>= 0`；
- 另外，`VueAnalyzer.isBusinessComponent()` 解析失败时默认返回 `true`。

这会导致 `0 分` 的通用组件，或者分数字段异常的组件，仍然进入覆盖清单并继续被 LLM 处理。

**触发场景**：
- 通用组件被打成 `0.0`；
- `businessScore` 字段未来格式变化、解析失败；
- 共享目录中的基础组件数量较多时。

**整改方案**：
- 抽取统一的业务组件判定函数，供 Analyzer 和 Generator 共用；
- 明确两类阈值：
  - “是否需要 LLM 摘要”；
  - “是否进入覆盖清单”；
  如果阈值不同，要配置化并写清楚语义；
- `businessScore` 解析失败时默认排除，而不是默认纳入。

**验收标准**：
- `0 分` 通用组件不会进入覆盖清单；
- 解析失败的组件不会误判为业务组件；
- 业务组件过滤逻辑在 Analyzer / Generator 中完全一致。

### 2.4 项目列表存在 N+1 查询

**严重度**：P2  
**影响范围**：项目列表 / 数据库查询性能

**相关文件**：
- `E:\java_project\AICaseTest\backend\src\main\java\com\testagent\service\ProjectService.java:119-129`
- `E:\java_project\AICaseTest\backend\src\main\java\com\testagent\service\ProjectAccessService.java:33-63`

**问题描述**：
`listProjects()` 先查出所有项目，再对每个项目调用两次 `getAccessLevel()`。而 `getAccessLevel()` 内部还会查用户、项目和组成员，形成典型 N+1。

**触发场景**：
用户项目数较多、组成员复杂、管理员查看大列表时。

**整改方案**：
- 把访问权限过滤下推到 repository/query 层；
- 或至少缓存当前用户信息和成员关系，避免重复查表；
- `listProjects()` 不要对同一项目重复计算访问级别。

**验收标准**：
- 项目列表 SQL 数量显著下降；
- 大列表场景下响应时间稳定；
- 不再出现同一项目重复查权限。

## 4. 代码质量正向项

下面几项我认为已经做得比较好，建议保留当前方向：

1. `PrdAgent` 做了基础 SSRF 防护，抓 URL 前有协议与内网地址约束；

3. 前端 SSE / 轮询 / `onUnmounted` 的清理整体比较完整；
4. 生产环境 `ProductionGuard` 已经把关键安全项往前推了一层；
5. 登录失败 5 次锁定的思路已经实现，属于可保留的基础安全措施。

## 5. 推荐实施顺序

### 第一批：必须修
1. 首次登录强制改密
2. SSE token 传递方式重构
3. `businessScore` 过滤口径统一
4. 项目列表 N+1 优化

### 第二批：建议修

---

## 6. 验收建议

修改完成后，建议按下面顺序验证：

- 后端单测：登录、改密、权限、`businessScore` 边界；
- 前端联调：首次登录强制改密弹窗、SSE 流式分析、生成页恢复；
- 回归：项目列表、项目详情、分析、生成、执行、管理接口；
- 若改了 SSE 鉴权，再验证 EventSource 断线重连与取消场景；
- 若改了 Telemetry，再跑一轮连续分析/生成，确认埋点不串线程。

---

## 7. 结论

当前实现**已经接近预期闭环**，但还不能算完全满足“可上线/可长期运行”的标准。最优先的三件事是：**首登强制改密、SSE token 安全、`businessScore` 口径统一**。这三项不修，安全和生成质量都会有明显缺口。
